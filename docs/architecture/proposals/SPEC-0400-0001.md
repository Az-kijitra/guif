## 1. 目的

SPEC-0400-0001は「フロント・Rust双方に標準テスト基盤を整備し、MVP機能全般に均等カバレッジを確保する」ことを求める。本書は、この方針を実現しやすくするためのアーキテクチャ上の設計(モジュール構成・テストシーム)を提案する。カバレッジの数値目標・E2E/CIの要否(ISS-0008)自体は本書の対象外であり、人間の判断に委ねる。

## 2. 前提: モジュール分割との関係

`docs/architecture/proposals/SPEC-0200-0001.md` で提案した機能単位(feature)モジュール構成、および同書4節の依存方向規定は、そのままテスト容易性の土台になる。旧`routes/viewer/+page.svelte`(2,675行)のような巨大な単一ファイルは、責務が絡み合っているためユニットテストの単位を切り出しにくい。feature単位かつ400行程度を目安に分割することで、各ファイルが独立してテスト可能な粒度になることを狙う(SPEC-0200-0001提案7節と同一の基準を適用)。本書はSPEC-0200-0001の構成を前提とするため、承認順序もSPEC-0200-0001を先行させる(ヘッダの承認順序制約を参照)。

## 3. フロントエンド

- SPEC-0400-0001 R-01の通り、vitestを標準テストフレームワークとして採用する(独自スクリプトである`run-key-tests.mjs`/`run-dnd-foundation-tests.mjs`のようなテストランナーには依存しない)。**vitestは新規の開発時依存関係(dev dependency)の追加である。** 本体の実行時依存ではないため影響範囲は限定的だが、明示しておく。
- 各featureディレクトリ内に実装ファイルと同居する形でテストファイル(例: `*.test.ts`)を配置する(colocation)。既存の`app/tests/keys/`のような空の別ディレクトリを新設しない。
- Tauriの`invoke()`を直接呼ぶロジックはテストが困難になりやすいため、`shared/ipc/`(SPEC-0200-0001 §4.5、feature別に分割済み)にIPC呼び出しをラップする薄いモジュールを設ける(既存の`tauri_fs.ts`/`tauri_git.ts`等と同様のパターンであり、新規パターンではない)。単体テストではこのラップ層をモックすることで、Tauriランタイムなしにfeatureロジックをテストできるようにする。

## 4. バックエンド(Rust)

- SPEC-0400-0001 R-02の通り、標準的なRustテスト基盤(`#[cfg(test)] mod tests`によるユニットテスト)を各モジュールに併設する。旧リポジトリでは`#[test]`が4ファイルにしか存在しなかった(既存調査3.4)状態を解消し、featureモジュールごとに対応するテストを持つことを基本とする。
- ファイルシステムを直接操作するテスト(`fs`, `fs_ops`, `archive`等)では、一時ディレクトリを用いた統合テストが必要になる。この際、**SPEC-0100-0005 R-06で明示的に除外されたStorage Provider抽象化(ResourceRef/StorageProviderBackendトレイト、`*_by_ref`系コマンド)を、テスト容易性の名目で再導入しないこと**に注意する。除外対象は「複数バックエンド(ローカル/クラウド)を実行時に切り替えるための抽象化」であり、テスト時のみ一時ディレクトリを使う手法(例: `tempfile`クレートによるテスト用一時ディレクトリの生成)はこれとは性質が異なるが、境界が紛らわしいため、architecture-guardianによる確認を必須とする。判定基準は4.1節の禁止リストを参照すること。
  - `tempfile`クレート(または同等)を**開発時依存(dev-dependency)として新規追加する**ことを提案する。実行時依存ではないため影響は限定的だが、外部依存の追加であることを明記する。
- 本体コード側に「テストのためだけの抽象化トレイト」を新設することは、現時点では提案しない(SPEC-0100-0005 R-06との境界が曖昧になりやすいため)。実ファイルシステム+一時ディレクトリによる統合テストを基本方針とする。

### 4.1 Storage Provider再導入の禁止リスト(architecture-guardian指摘 MUST-1 対応)

テスト容易性向上を名目とした場合であっても、以下のいずれかが新プロダクトのコード(フロント・バックエンド問わず)に現れた場合は、**SPEC-0100-0005 R-06/R-08違反として差し戻す**。architecture-guardianはコードレビュー時に本リストを判定基準として用いること。

1. ファイルシステムアクセスを抽象化するtrait(Rust: `trait StorageProvider`/`FileSystem`/`FsBackend`/`Backend`等、FS操作の集合を定義するtrait全般)。**(SHOULD-24a対応)** TypeScript側の等価物として、FS操作の集合を定義する抽象interface(`interface StorageProvider`/`FileSystemAdapter`/`FsBackend`等)も同様に該当する。
2. 本番関数のFS操作をジェネリクス化(Rust: `fn foo<B: Backend>(...)`等)またはdyn化(`Box<dyn ...>`、`&dyn ...`等)すること。**(SHOULD-24a対応)** TypeScript側では、FS操作関数の実装をコンストラクタ注入・関数注入で差し替え可能にする設計(例: `createFsClient(backend: Backend)`のような、実行時にバックエンド実装を切り替える引数を本番コードのAPIに持たせること)がこれに相当する。
3. パス以外の抽象識別子型(`ResourceRef`相当。scheme付き文字列(例: `local://`, `provider://`)を解釈・生成する型を含む)。**(SHOULD-24a対応)** TypeScript側では、`ResourceRef`相当の型エイリアス/interface定義、`invoke("*_by_ref", ...)`のように`*_by_ref`を含む文字列リテラルでコマンドを呼び出す箇所、および`local://`/`provider://`等のscheme付き文字列を組み立てる処理(テンプレートリテラル・文字列結合を含む)が該当する。
4. `*_by_ref`という命名のコマンド/関数、`get_capabilities`系のバックエンド能力問い合わせAPI、および型・モジュール名に`Provider`/`Registry`/`Capability`という語を含むもの。**(MUST-16対応: 除外条項)** ただし、キー入力→コマンドID→ハンドラのディスパッチのみを行う「コマンドレジストリ」機構(`docs/architecture/proposals/SPEC-0200-0001.md` §4.1経路1./§4.3で必須機構として規定される`shared/`配下のコマンドレジストリ/イベント通知の仕組み、および`CommandRegistry`等その実装)は、ストレージバックエンドの能力問い合わせ・実行時切替を一切行わないため本項には該当しない。この除外は「コマンド名/ハンドラ名の登録・解決」を行う機構に限定され、ファイルシステム操作のバックエンドを抽象化・切替する目的の`Registry`(例: `StorageProviderRegistry`)には適用されない。
5. **(SHOULD-24b対応: 導入意図ではなく観測可能な条件へ書き換え)** 本番ビルドの実行経路(`#[cfg(test)]`以外のモジュール・関数)から参照されるトレイト/Cargo featureのうち、実装型(`impl`)がテストコード(`#[cfg(test)]`配下)にしか存在しないもの。判定は「テスト目的での導入意図」という主観ではなく、「本番ビルド時に到達可能なコードから当該トレイト/featureが参照されており、かつそのトレイトの実装がテストコード以外に存在しない」という機械的に検出可能な状態の有無で行う。

**許容されるのは、`#[cfg(test)] mod tests`内でのみ`tempfile::TempDir`を生成し、本番関数(通常のパス引数を取る関数)に実パス(`&Path`/`PathBuf`)を渡す形のみである。** 本番コード側にテスト専用の抽象化・分岐を持ち込まないこと。

**(SHOULD-24c対応: 誤検出時の例外手続き)** 上記1〜5をgrep等の機械的検出で運用する場合、外部クレート/ライブラリ由来の名称(例: サードパーティ製ORMの`Registry`型を単に利用しているだけの場合)等により誤検出することがあり得る。誤検出と判断される場合は、当該箇所にコメントで理由を明記した上でarchitecture-guardianに申告し、判断結果と理由を`docs/architecture/traceability.md`の「注意事項」節(または後続で設ける例外記録表)に記録すること。記録なしに機械的検出結果を独断で無視してはならない。

## 7. architecture-guardian 再検証所見(2026-09-22 第2回・条件付き承認)

MUST-1(Storage Provider再導入の禁止リスト)および承認区分のREQUIRES_HUMAN_APPROVALへの格上げ・承認順序制約の明記は、実質を伴って対応されたことを確認した。§4.1はRustコードに対しては概ね機械判定可能な水準にある。ただし以下を解消した版をもって人間承認に付議すること。**本書は引き続き REQUIRES_HUMAN_APPROVAL を維持し、SPEC-0200-0001の人間承認前に単独承認しないこと。**

### MUST

- **MUST-16(禁止リストと他提案の正面衝突): §4.1-4 の禁止語`Registry`が、SPEC-0200-0001 §4.1経路1.・§4.3で必須機構と規定された「コマンドレジストリ」と衝突する。** 現状の禁止リストを機械適用すると、SPEC-0200-0001が義務づける機構そのものが差し戻し対象になる。§4.1-4に「キー入力→コマンドID→ハンドラのディスパッチを行うコマンドレジストリ(SPEC-0200-0001 §4.3)は、ストレージバックエンドの能力問い合わせ・切替を行わない限り本項に該当しない」旨の除外を明記するか、SPEC-0200-0001側の機構名を改めること(いずれか一方で可。両提案で表記を揃えること)。

### SHOULD

- SHOULD-24a: §4.1柱書は「フロント・バックエンド問わず」と宣言しているが、判定基準1・2はRust固有の語彙(trait、ジェネリクス、`Box<dyn>`)で書かれており、フロント側の等価物が列挙されていない。TypeScript側の具体パターン(`interface StorageProvider`/`FsBackend`等のFS抽象interface、`ResourceRef`相当の型エイリアス、`invoke("*_by_ref")`の文字列リテラル、`local://`/`provider://`を組み立てる処理)を追記すると、フロントに対しても機械判定が成立する。
- SHOULD-24b: §4.1-5「`#[cfg(test)]`以外から参照される、**テスト目的で導入された**トレイト/フィーチャフラグ」は導入意図に依存する基準であり、機械的には判定できない。「本番ビルドに含まれる経路から参照されるトレイト/Cargo feature のうち、テストコードのみが実装型を提供するもの」等、観測可能な条件に書き換えることを推奨する。
- SHOULD-24c: 禁止リストを実際にgrep等で運用するなら、誤検出時の扱い(例外を認める手続き・記録先)を1行添えること。現状は例外規定がないため、外部クレート由来の名称等で機械的に引っかかった場合の判断が属人化する。

## 8. architecture-guardian 再検証所見(2026-09-22 第3回・承認可)

MUST-16は§4.1-4の除外条項によって解消されたことを確認した。除外の範囲が「キー入力→コマンドID→ハンドラのディスパッチ」という肯定的定義で限定され、非該当例(`StorageProviderRegistry`)も併記されているため、`SPEC-0200-0001.md`§4.1経路1./§4.3が必須機構とする「コマンドレジストリ」が禁止リストに抵触しないことは一意に読める。両書の表記も衝突していない。SHOULD-24a/b/cもいずれも実質を伴って対応済みであり、特に§4.1-5は観測可能条件(本番ビルド到達経路からの参照+実装型が`#[cfg(test)]`配下のみ)へ書き換えられ、機械判定が成立する水準になった。

**判定: 本書は構造面で承認可。** 承認区分 **REQUIRES_HUMAN_APPROVAL**(新規dev依存2件)および承認順序制約(`SPEC-0200-0001.md`の人間承認前に単独承認しない)は引き続き維持すること。

### SHOULD(記録に留める。承認を妨げない)

- SHOULD-31: §4.1-4の除外判定条件「ストレージバックエンドの能力問い合わせ・実行時切替を一切行わない」は、肯定的定義と併用される限り運用可能だが単独では主観判定の余地がある。grep運用の初期設定として、除外対象を**パス+識別子の具体リスト**(例: `app/src/lib/shared/command-registry.ts`の`CommandRegistry`)として`docs/architecture/traceability.md`の「注意事項」節(SHOULD-24cの記録先)に先行登録しておくと、実コード生成時の判断が属人化しない。
- SHOULD-32: §4.1-4の除外条項中の「`CommandRegistry`**等**その実装」の「等」が唯一の曖昧点。上記の具体リスト化で解消可能。
- SHOULD-34: 指摘番号の衝突。本書§7のSHOULD-24a/b/cと`SPEC-0200-0001.md`§10のSHOULD-24(記法統一)は別物である。今後の指摘番号は文書横断で一意に採番すること。
