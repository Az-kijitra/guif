# 提案: ドキュメント構成のアーキテクチャ(SPEC-0500-0001対応)

## 1. 目的

SPEC-0500-0001は「実装と一致した正確なドキュメント」「実在しないパスを残さない」「CHANGELOGを単一の正とする」「配布物同梱ドキュメントも対象」を求める。旧リポジトリでは以下の不整合が確認されている(既存調査3.1、4)。

- README参照パス(`docs/development_guide.md`等)の不在
- ルート`CHANGELOG.md`とdocs配下`CHANGELOG.md`の2重管理・内容不一致
- 配布同梱マニュアル(`app/src-tauri/resources/user_manual.*.md`)がルートのマニュアルと別ファイルとして重複管理され、撤去済み機能の記述が残存

本書は、これらを構造的に再発させないためのドキュメント配置・生成の仕組みを提案する。ドキュメントの種類・対応言語そのもの(ISS-0009)は本書の対象外。

## 2. ドキュメント配置(単一の正)

```
<repo-root>/
├── README.md              … 唯一のトップレベル案内。参照先は全て実在確認済みのパスのみ記載
├── CHANGELOG.md            … 単一のCHANGELOG(SPEC-0500-0001 R-04)。docs/配下に重複を作らない
└── docs/
    ├── user_manual.md          … ユーザーマニュアル(正)
    ├── (対応言語が決まれば ja/ 等のミラー構成。ISS-0009待ち)
    └── ...(開発ガイド等を設ける場合もこの配下に集約。種類自体はISS-0009で決定)
```

- 「正」の置き場所を1箇所に定め、README・配布物からはこの1箇所を参照する。旧リポジトリのようにルート直下と`docs/`配下に同種のドキュメントを重複配置しない。

## 3. 配布同梱ドキュメントの二重管理防止(SPEC-0500-0001 R-07への対応、新規の小さな仕組み)

- 旧リポジトリでは配布用`app/src-tauri/resources/user_manual.*.md`が`docs/user_manual.md`相当のファイルと別に手動管理され、内容の乖離(撤去済みGoogle Drive機能の記述残存)が生じた。
- 提案: 配布物同梱ドキュメントは**手動で複製・別管理しない**。ビルド時に`docs/`配下の正本を`app/src-tauri/resources/`へコピーする小さなビルドステップ(スクリプトまたはTauriのbeforeBuildフック)を設け、実体を単一化する。
- これは新しいビルド時の仕組み(小さな新規要素)であるため、architecture-guardianでの確認を推奨するが、外部依存の追加や既存レイヤー構造の変更は伴わないため、大きな構造変更には該当しないと考える。

### 3.1 生成物の非コミット・スコープ外語の禁止(architecture-guardian指摘 SHOULD-9 対応)

- (a) ビルド時に`docs/`配下の正本から`app/src-tauri/resources/`へ複製される成果物は、**`.gitignore`対象とし、リポジトリへコミットしない。** 複製物を手動編集・手動コミットしてしまうと、複製が「第二の正」となり旧リポジトリと同じ二重管理・内容乖離を再発するため、生成物であることを構造的に保証する。
- (b) 製品同梱ドキュメント(配布物に含まれるマニュアル等、ビルド時生成物を含む)には、スコープ外機能を示す語(「Git連携パネル」「WinMerge」「デュアルペイン」「Storage Provider」「Google Drive」)を一切含めない(SPEC-0100-0005 R-07/R-08)。複製元である`docs/`配下の正本自体にこれらの語が含まれないことを一次的な担保とし、architecture-guardianはリリース物のドキュメントレビュー時にこれらの語の残存を確認すること。

## 4. パス整合性の自動チェック(SPEC-0500-0001 R-03)

- README/ユーザーマニュアルが参照するファイルパスの実在確認を、可能であればCIまたはローカルスクリプトで自動化することを推奨する(例: Markdown内のリンクを走査し、リポジトリ内相対パスが存在するかを確認する軽量スクリプト)。
- これはSPEC-0400-0001のテスト基盤整備と合わせて導入すると効率的である(同じCI/スクリプト基盤に相乗り可能)。
- 具体的な自動化手段の要否・実装方法はISS-0009の解消と合わせて確定すること。本書は「望ましい」という設計上の推奨に留め、確定要件とはしない。

## 5. 本書で解決しない事項

- ドキュメントの種類(開発ガイド・保守ガイド・ADR等の要否)、対応言語(ISS-0009)。
- 多言語版の内容一致(SPEC-0500-0001 R-06)を人手レビューで担保するか自動チェックするかの最終決定。
