## 1. 前提と適用範囲

- 新規リポジトリはゼロベース再構築(SPEC-0100-0002 R-01)であり、旧`ReflexFiles`リポジトリには対応する「既存アーキテクチャ」が新リポジトリ側に存在しない。本提案は旧リポジトリの構造(既存調査 2.1〜3.3)を反面教師・参考情報として用いつつ、新規にモジュール境界を設計するものである。
- したがって本提案は役割定義でいう「既存パターン踏襲の小変更」ではなく、「新規モジュール・境界の追加」に該当する。**REQUIRES_HUMAN_APPROVAL** とし、architecture-guardianの検証と人間承認を経るまでcode-generatorには進めないこと。
- 新リポジトリ名・配置パス・製品の正式名称は未確定(ISS-0002)であるため、本書のディレクトリ例は `<repo-root>/` を仮のルートとして記述する。名称確定後もモジュール境界自体は変わらない想定。
- 本書はSPEC-0400-0001(テスト容易性アーキテクチャ)の前提となる。承認順序制約(ヘッダ参照)により、SPEC-0400-0001は本書の人間承認前に単独承認してはならない。

### 3.1 確定: 検索処理の配置とfeature間連携(SPEC-0300-0012関連、ISS-0056解消。2026-09-24 architecture-mapper)

APPROVED済み詳細仕様 **SPEC-0300-0012**(検索。前版SPEC-0300-0004はDEPRECATED)のR-127〜R-131により、検索機能のバックエンド非存在・フロントエンド完結という基本方針は確定した。本節はそれを踏まえ、旧版が「新規決定事項」として残していた**feature間連携経路の確定**(SPEC-0300-0012 R-129-1、ISS-0056)を記す。

#### 3.1.1 バックエンド非存在(確定・変更なし)

- 検索専用のバックエンドコマンド・モジュールは追加しない(SPEC-0300-0012 R-127)。既存の`fs_list_dir`(`fs/`)の結果に対し、フロントエンドの`features/search/`で完結する絞り込みを行う。
- `shared/ipc/`への新規ラッパも追加しない(R-130)。Storage Provider抽象化・`*_by_ref`系コマンドも用いない(R-131、SPEC-0100-0005 R-06)。

#### 3.1.2 `entries` / `filteredEntries` の所有者とfeature間連携経路(ISS-0056の解消)

**結論: SPEC-0300-0012 R-129が列挙する3経路のうち、②`routes/`層での合成のみを用いる。新規の`shared/state/`所有モジュールは追加しない。**

判断根拠:

1. **Phase 1実装の調査結果**: `app/src/lib/features/file-list/list-state.svelte.ts`は`entries`を feature ローカルの`$state`として保持し、冒頭コメントで「他featureから読まれないfeatureローカル状態(§5.1)」と明記している。一方、`app/src/lib/features/file-list/navigation.ts`・`selection.ts`の**純粋関数群**(`moveFocusRow(visible, index, direction)`、`moveFocusColumn(index, direction, rowsPerColumn, totalCount)`、`selectAllVisible(visible)`、`invertSelectionVisible(visible, selected)`、`filterFocusableEntries(all, visible)`等)は、SPEC-0300-0009 R-54〜R-56(「focus traversal only considers entries that are currently visible」等のコメントが既に付与されている)の時点で、**「全件(all)」と「表示中(visible)」を別々の引数として受け取れる形に既に設計されている。** 現在この区別が使われていない(`list-state.svelte.ts`が`entries`を両方の役割に流用している)だけであり、Phase 1の設計はもともと検索によるフィルタリングを見越した形になっていた。
2. **`shared/state/`所有モジュール化(経路③)を採らない理由(SHOULD-42(b)対応、論理の飛躍を修正)**: `entries`を`shared/state/`へ昇格させる案も検討したが、(a) `entries`をfile-listローカルに留める判断自体はSPEC-0300-0009 R-75から直接導かれるものではない(**R-75は「配列の保持」と「index基準」を規定するのみで、モジュール所有権・feature境界については何も規定していない**。旧版の「R-75により file-list 側の内部基準であり続けるべき」という記述は論理が飛躍していたため訂正する)。`entries`を書き込む唯一の主体(`loadDirectory`)が今後もfile-list feature内に留まるのが自然であるという、feature境界設計として独立の判断である。(b) `filteredEntries`は本質的に「`entries` + 検索クエリ/モード/アクティブ状態」から導出される**純粋な計算結果**であり、Svelteの`$derived`によって表現するのが最も自然でありstate として「所有」する必要がないこと、(c) 新規共有状態を導入すると§5.2の登録・architecture-guardian確認の手続きが発生し、SPEC-0100-0005 R-06(過度な抽象化の禁止)・本タスクの指示(検索1機能のための最小限の連携)に照らして正当化しにくいこと、の3点から採用しない。
3. **`shared/`のレジストリ/イベント(経路①)を採らない理由**: R-116の再計算契機(`entries`/アクティブ状態/クエリ/正規表現モードの4入力)はいずれも高頻度(キー入力ごと)に変化しうる値であり、これをイベント通知の形にすると`shared/`側に検索固有の再計算タイミング制御ロジックを持ち込むことになり、`shared/`が`features/`に依存しないという原則(§4.1末尾)との整合が取りにくい。`$derived`による合成で十分に要件(R-110 デバウンスなし・AC-105 同一評価タイミング)を満たせるため、イベント機構は不要と判断した。

**具体的な設計(経路②: `routes/`層での合成):**

- `app/src/lib/features/search/matching.ts`(新規): DOM/Tauriに依存しない純粋関数として、部分一致・正規表現マッチング(R-111〜R-114)と`computeFilteredEntries(entries, { active, query, regexMode }) → { filteredEntries, error }`(R-115〜R-118)を実装する。R-128-1/AC-129に対応し、`features/search/matching.test.ts`で単体テストする。
- `app/src/lib/features/search/search-state.svelte.ts`(新規、`list-state.svelte.ts`と対になるfeatureローカル状態): `active` / `query` / `regexMode` / `history`(R-105〜R-109, R-113, R-121, R-122 相当のUI状態)を保持する。**`filteredEntries`と`error`はこのモジュールの状態としては保持しない**(理由は上記2)。他featureからは読まれないfeatureローカル状態(§5.1)のままとする。
- `app/src/routes/+page.svelte`(既存の合成層): `fileListState`(file-list)と`searchState`(search)の両方をimportし、次の`$derived`で両者を橋渡しする。

      active: searchState.active,
      query: searchState.query,

  これは既存の`let layout = $derived(fileListState.layout(containerWidth || 800, containerHeight || 400));`(routes/+page.svelte、Phase 1から存在)と同型の「複数featureの公開値を読み取り、既にテスト済みの純粋関数へ渡すだけ」の合成であり、§4.1 SHOULD-19が禁じる「状態の保持」「業務ロジック」のいずれにも該当しない(実際のマッチングアルゴリズムは`features/search/matching.ts`側にあり、routes側は呼び出すだけ)。
- **一覧の描画**: routesの`{#each}`は`fileListState.entries`ではなく`filteredEntries`を対象にする(R-115)。`<SearchBar>`コンポーネント(`features/search/`)へは`error={filterResult.error}`をpropsとして渡す(R-113-3/113-4。search-state側に同期用`$effect`を持たない、単純なprops受け渡し)。
- **フォーカス移動・選択操作の絞り込み範囲限定**(R-109-2-2、R-123 / SPEC-0300-0009 R-55): `list-state.svelte.ts`のラッパー関数(`moveRow` / `moveColumn` / `selectFocused` / `toggleFocused` / `openFocused` / `goParent` / `layout`)を、内部で`entries`を直接参照する形から、**呼び出し側(routes)が渡す「表示中配列(`filteredEntries`)」を明示的な引数として受け取る形**へシグネチャ変更する(内部で呼んでいる`moveFocusRow`等の純粋関数は既にこの形の引数を受け付けるため、ラッパー層のみの変更で済む、上記1参照)。routesは検索の有無にかかわらず常に`filteredEntries`を渡す(R-117により非アクティブ時は`entries`と同一内容になるため、routes側で`if (searchActive)`のような分岐を書く必要はない)。

#### 3.1.3 `focusedIndex`の格納基準と視覚⇔実インデックス変換(MUST-37対応)

**結論: `focusedIndex`は常に`entries`(実配列)基準のインデックスとして格納する(SPEC-0300-0009 R-75「選択/フォーカスのインデックス基準として列挙結果の配列を並行して保持する」に整合、Phase 1の格納方式から変更なし)。移動計算(moveRow等)は表示中配列(filteredEntries)を基準とした「視覚インデックス」空間で行い、計算結果を実配列インデックスへ変換してから格納する(SPEC-0300-0009 R-56)。**

第3次改訂時点の設計は、`focusedIndex`の格納基準を明言しないまま「ラッパーにfilteredEntriesを渡せば済む」としていたが、これは具体的に破綻する(例: `entries`100件・`filteredEntries`3件・`focusedIndex=57`のとき、`moveFocusRow(filteredEntries, 57, "down")`は範囲外アクセスとなり、表示されていない別のエントリを指してしまう)。architecture-guardian指摘(MUST-37)を受け、以下の変換レイヤーを追加する。

**新設する純粋関数(`app/src/lib/features/file-list/navigation.ts`、R-56対応。unit-test-writerのテスト対象):**

```ts
// R-56: convert a real (entries-basis) index into a visual index (position
// within the currently displayed/visible array), via path identity.
// Returns -1 if the entry at realIndex is not present in `visible` (i.e.
// currently filtered out). Callers must treat -1 defensively (see below);
// in normal operation this should not occur: while the search bar is closed,
// `visible` mirrors `entries` in full (R-117), so every real index is
// trivially visible; while the search bar is open, R-120 prevents this
// function's callers (moveRow etc.) from being invoked at all (the list
// only regains focus via R-109-2's resolveFocusIndexForVisibleSet, which
// guarantees the resulting real index is visible).
export function toVisualIndex(
  realIndex: number,
  entries: readonly { path: string }[],
  visible: readonly { path: string }[],
): number;

// R-56: convert a visual index (position within `visible`) back into a real
// (entries-basis) index, via path identity. Returns -1 if out of range.
export function toRealIndex(
  visualIndex: number,
  entries: readonly { path: string }[],
  visible: readonly { path: string }[],
): number;

// R-109-2-1 ONLY (SHOULD-45 fix: this function previously claimed to also
// serve R-107-1's close-time transition, but the two rules are NOT
// equivalent — R-107-1 rule 2 focuses the listbox root element without
// changing focusedIndex at all, whereas R-109-2-1 rule 2 moves focusedIndex
// to filteredEntries[0]. §3.1.5's close-time design does not call this
// function; it only calls containerEl?.focus() (focusedIndex is left
// untouched, per the ISS-0057(b) answer below). This function implements
// R-109-2-1's 3-rule priority exclusively, used when Enter confirms a
// filtered search and focus moves from the search input into the list:
//   1. if the entry at currentRealIndex is present in `visible`, keep it
//      (return currentRealIndex unchanged)
//   2. else, return the real index of `visible[0]` (filteredEntries' first
//      entry)
//   3. else (visible is empty), return null — caller must not move focus
//      into the list and must leave it in the search input (R-109-2-1 item 3)
export function resolveFocusIndexForVisibleSet(
  entries: readonly { path: string }[],
  visible: readonly { path: string }[],
  currentRealIndex: number,
): number | null;
```

#### 3.1.4-1 `inputFocused`のリセット責任(MUST-43対応、新設)

**問題**: 検索バーが閉じる経路(R-106の3経路: Escape / Clearボタン / 空クエリでの確定)では検索`<input>`要素がDOM(条件描画)から外れる(R-103)。ブラウザ実装によっては、要素がアンマウントされる際に`blur`イベントが発火しない場合がある。`onfocus`/`onblur`のみに頼って`inputFocused`を管理すると、この経路で`inputFocused`が`true`のまま取り残され、以後R-14-2が恒久的に真であり続け、`Ctrl+Q`/`Ctrl+,`(優先1)以外の**全てのグローバルショートカット・一覧操作が恒久的に抑止され続ける**という重大なバグに陥る。

**結論: `features/search/search-state.svelte.ts`が公開する`inputFocused`は、`onfocus`/`onblur`で追跡する生の値そのものではなく、`active && (生のフォーカス追跡値)`という導出値(`$derived`相当)として公開する。**

- 内部的には、`onfocus`/`onblur`で更新される生の真偽値(以下`rawFocused`、非公開)と、検索バー自体のアクティブ状態`active`(R-103、既存)の2つを保持する。
- 公開getter`inputFocused`は`active && rawFocused`を返す。
- `active`は検索バーが閉じるR-106の3経路すべてにおいて、`search-state.svelte.ts`自身の`cancel()`/`confirm()`(空クエリ確定時)等の**関数呼び出しによって確実に`false`へ設定される**(DOMイベントに依存しない、モジュール内の明示的な状態遷移である。既存のR-103/R-108の設計により保証済み)。したがって、`rawFocused`がブラウザの`blur`未発火により`true`のまま取り残されたとしても、`active`が`false`になった時点で公開getter`inputFocused`は即座に`false`を返すようになり、R-14-2の抑止が解除される。
- **§3.1.5の`containerEl?.focus()`(R-107)には依拠しない。** アンマウント順序・フォーカス移動のタイミングに依存する不安定な回避策ではなく、`search-state.svelte.ts`内部の状態導出のみで自己完結的に解消する設計とする(guardian指摘の通り)。
- unit-test-writerのテスト対象: `search-state.svelte.ts`の`inputFocused`ゲッターについて、(a) `rawFocused=true, active=true`→`inputFocused=true`、(b) `rawFocused=true`のまま`active`を`false`にする(`blur`未発火を模擬)→`inputFocused=false`になること、を検証すること。

#### 3.1.4-2 `toRealIndex`が解決不能な場合の防御規定(MUST-44対応、新設)

**問題**: `toVisualIndex`の`-1`フォールバック(視覚インデックス`0`とみなす)は§3.1.3で規定済みだが、`toRealIndex`側の`-1`(対応する実インデックスが見つからない)の扱いが未規定だった。具体的には、`visible`(filteredEntries)が0件のとき`toggleFocused()`が`applySelectToggle`経由で視覚インデックス`0`を返し、`toRealIndex(0, entries, [])`が`-1`になりうる。`focusedEntry()`は`entries`基準で無条件に解決するため、フォーカス中の実エントリが現在`visible`に含まれない状態で`toggleFocused`/`selectFocused`が呼ばれると、**非表示のエントリを選択してしまい、R-123(選択操作はfilteredEntriesの範囲に限る)に違反する。**

**結論(防御規定、§3.1.3に追加する契約):**

1. **`visible.length === 0`の場合、`moveRow` / `moveColumn` / `toggleFocused` / `selectFocused`はいずれも即座にno-op(何もしない)とする。** 呼び出し前に`if (visible.length === 0) return;`相当のガードを置く。これにより`toRealIndex`が空配列に対して呼ばれること自体を防ぐ。
2. **選択を変更する操作(`toggleFocused` / `selectFocused`)は、実行前に「現在フォーカス中の実エントリが`visible`に含まれているか」を`toVisualIndex(focusedIndex, entries, visible) !== -1`で確認し、含まれていなければno-opとする。** これにより、`visible.length > 0`だが現在のフォーカス対象がたまたま非表示という状況でも、非表示エントリの選択・トグルが発生しない(R-123の遵守)。
3. **上記1・2を満たしていてもなお`toRealIndex(...)`が`-1`を返した場合(実装上の不整合等に対する最終防御線)、呼び出し元は`focusedIndex`を更新しない(直前の値を保持する)。** `-1`という無効な値を`focusedIndex`へ書き込んではならない。
4. unit-test-writerのテスト対象: (a) `visible`が空配列のとき`moveRow`/`moveColumn`/`toggleFocused`/`selectFocused`がいずれも状態を変化させないこと、(b) `visible`が非空だがフォーカス中の実エントリが`visible`に含まれない状態で`toggleFocused`/`selectFocused`を呼んでも選択状態が変化しないこと、(c) `toRealIndex`が`-1`を返す入力に対し、呼び出し元ラッパーが`focusedIndex`を書き換えないこと。

#### 3.1.5 フォーカス制御(DOM操作)の所有者(MUST-39対応)

SPEC-0300-0012のR-105/R-105-1(起動時に検索入力欄へ)、R-107/R-107-1(終了時に一覧へ復帰)、R-109-2-1(確定時に一覧の該当行へ)は、いずれもDOM上の命令的なフォーカス移動を要求する。以下の通り所有者を確定する。

**結論: 命令的な`.focus()`呼び出しは`routes/+page.svelte`が一元的に行う。「どのインデックス/要素を対象にするか」という決定ロジックは各featureの純粋関数・状態モジュールに閉じ込め、routesは決定結果を受け取って`.focus()`を呼ぶだけの薄いシーケンサに徹する。**

- **前提(既存実装の確認)**: `app/src/lib/features/file-list/aria.ts`の`computeFileListAria`が示す通り、file-listは**ARIAリストボックスの複合フォーカスパターン**を採用している(実DOMフォーカスは常に`role="listbox"`のコンテナ要素〈`tabindex="0"`〉に置かれ、`aria-activedescendant`が論理的にフォーカス中の行を指す。行要素自体は個別にフォーカスされない)。これにより、MUST-39が要求する「行への個別フォーカス」は実際には「コンテナへの`.focus()`呼び出し」1つに単純化される(行ごとのDOM参照や`tabindex="-1"`per-row化は不要)。
- **R-105/R-105-1(検索起動時)**: routesの`search`アクション用ディスパッチハンドラ(`onListAction`の`case "search"`、§3.1.2/§3.1.4)内で、`searchState.open()`呼び出しの直後に`searchInputEl?.focus()`を呼ぶ(`searchInputEl`は`<SearchBar>`から`bind:this`等でroutesへ公開される参照)。**R-105-2(既にアクティブな状態での再発火)も同じコード経路で自然に満たされる**(状態の遷移〈false→true〉ではなく、アクション発火のたびに無条件で`.focus()`を呼ぶため、`$effect`による状態差分監視ではなく明示的な呼び出しを用いる)。
- **R-107/R-107-1(検索終了時)**: `searchState`の`cancel()`(Escape/Clearボタン)呼び出し元、および空クエリでの確定(R-109-1)を処理するroutes側のコールバック内で、`containerEl?.focus()`を呼ぶ(`containerEl`は既存のPhase 1実装で`bind:this={containerEl}`として既に取得済みの参照であり、新規追加は不要)。R-107-1の「①現在フォーカス中の行が表示されていればその行、②なければ一覧のルート要素」という優先順は、**行への個別フォーカスを行わない複合フォーカスパターンにより自動的に解決される**(常にコンテナへフォーカスし、`aria-activedescendant`が有効な行を指すか、非表示なら§3.1.3のR-119処理により属性自体が付与されない。いずれの場合もコンテナへの`.focus()`という1種類の操作で足りる)。**この`containerEl?.focus()`呼び出しは`inputFocused`(R-14-2向けの真偽値)のリセットには一切関与しない(MUST-43対応の注記)。`inputFocused`のリセットは§3.1.4-1が定める`active && rawFocused`という導出により`search-state.svelte.ts`内部で自己完結し、DOMフォーカス移動のタイミングやアンマウント順序には依存しない。**
- **R-109-2-1(確定時)**: `<SearchBar>`のEnterキー処理(§3.1.4、`onSearchAction("confirm")`)を受けるroutes側のコールバックが、(1) `searchState.confirm()`(履歴追加等、search feature内のビジネスロジック)を呼び、(2) `resolveFocusIndexForVisibleSet(fileListState.entries, filteredEntries, fileListState.focusedIndex)`(§3.1.3、file-list feature内の純粋関数)を呼んで対象の実インデックスを決定し、(3) 結果が`null`でなければ`fileListState.focusIndex(result)`(§3.1.3の新規公開更新関数)で状態を更新してから`containerEl?.focus()`を呼ぶ。結果が`null`(filteredEntriesが0件、R-109-2-1のルール③)の場合は何もせず、フォーカスは検索入力欄に残ったままとする。
- **SHOULD-19との整合**: 上記のroutes側コード(`.focus()`の呼び出し自体)は、決定ロジック(どのインデックス・どちらの要素か)を一切含まず、feature側が既に決定・計算した結果を受け取ってDOM APIを呼ぶだけの**環境結合コード**である。これはPhase 1から既にroutesに存在する`attachGlobalKeydownListener(window, keydownHandler)`(`onMount`内の命令的なDOM/ブラウザAPI呼び出し)と同種の扱いであり、SHOULD-19が禁じる「業務ロジック」(バリデーション・分岐によるコマンド実行・データ変換)には該当しないと判断する。ただし本判断はarchitecture-guardianの確認を推奨する(§9の申し送りに追加済み)。
- **新規に必要な参照**: `searchInputEl`(`<SearchBar>`の検索`<input>`要素への参照。現状未実装、新規追加が必要)。`containerEl`(file-listのコンテナ要素、Phase 1で既に実装済み、変更不要)。

## 4. 依存方向の明文規定(architecture-guardian指摘 MUST-2 対応)

レイヤー間・feature間の依存方向を以下の通り明文化する。実装段階でこれに反する`import`/`use`が検出された場合はレイヤー境界違反として差し戻す基準とする。

### 4.1 フロントエンドの依存方向

- 依存方向は `routes/ → features/ → shared/` の一方向のみ。逆方向(`shared/`から`features/`を参照、`features/`から`routes/`を参照)のimportは禁止する。
- **features/間の直接importは禁止する。** 例: `features/file-list/`から`features/keyboard/`の内部モジュールを直接importしない。
- feature間の連携が必要な場合は、以下のいずれかの経路に限定する。
  1. `shared/`に置くコマンドレジストリ/イベント通知の仕組み(feature側は自分自身の名前でハンドラを登録・イベントを購読するのみで、他featureの内部実装を知らない)
  2. `routes/`層での合成(複数featureのコンポーネント・ハンドラをroutes層で組み合わせる)
  3. **(SHOULD-20対応・第3経路として追加)** 5.2節の共有状態所有モジュール経由(featureが共有状態を「読む」/所有モジュールの公開更新関数を通じて「更新する」)。これは状態の共有であり、他feature内部実装への直接依存ではない。feature間連携は上記1〜3のいずれかの経路に限定し、これ以外の経路(featureディレクトリ間の直接import等)は許容しない。
- **SHOULD-19対応: `routes/`層での合成(経路2)として許される範囲を以下に限定する。**
  - `routes/`は状態を保持しない(状態は必ずfeatureローカルまたは5.2節の共有状態所有モジュールに置く)。
  - `routes/`は業務ロジック(バリデーション、コマンド実行の分岐、データ変換等)を持たない。あくまで複数featureのコンポーネント・ハンドラの配置・受け渡しのみを行う。
  - `routes/`配下の各ファイルにも7.1節の行数上限(400行目安)を適用する。これは旧`routes/viewer/+page.svelte`(2,675行)のような「合成層の肥大化」の再発を防ぐための基準である。

### 4.2 バックエンドの依存方向

- 依存方向は `app/(bootstrap) → <feature>/ → shared/` の一方向。`<feature>/`間の直接依存(例: `fs`モジュールから`keymap`モジュールを直接`use`する)は禁止する。
- feature間連携が必要な場合はTauriコマンド経由でフロント側が合成することを基本とし、Rust側でfeatureをまたぐ直接呼び出しは行わない。どうしても必要な場合は`shared/`に共通インターフェースを切り出し、architecture-guardianの確認を必須とする。
- **MUST-15対応: `config/`は`<feature>/`の一員ではなく、`app/`と`<feature>/`の間に位置する独立レイヤーである(2節参照)。** `config/`の依存方向は **`config/ → shared/` の一方向のみ**(永続化スキーマ型は`shared/schema/`に置く。エラー型・パスユーティリティ等`shared/`の他モジュールへの依存は許容する。MUST-27対応)とし、`config/`が`<feature>/`を直接参照すること、および`<feature>/`が`config/`を直接参照することのいずれも禁止する(循環依存の回避)。読込済み設定・履歴データをfeatureへ渡す経路は`app/`(bootstrap)による起動時注入に限定する(**MUST-26対応**: Rustプロセス内で`<feature>/`のコマンドハンドラが`config/`をTauriコマンド越しに「呼び出す」機構は存在しないため、Rust側`<feature>/`から`config/`への実行時アクセスは行わない。「Tauriコマンド経由」はフロントエンドfeatureが`shared/ipc/config.ts`を介して`config/`のTauriコマンドを呼ぶ場合のみを指す。詳細は6節を参照)。

### 4.3 keyboardの責務限定(ハブ化の回避)

- `keyboard`(フロント`features/keyboard/`、バックエンド`keymap/`)は「キー入力→コマンドIDの対応関係」の保持・解決のみを所有する。コマンドの実体(実行ロジック)は一切持たない。
- 各featureは自身が提供するコマンドのハンドラを、4.1項1.のコマンドレジストリに自ら登録する。`keyboard`はキー入力をコマンドIDへ変換してレジストリへディスパッチするだけであり、他featureをimportしてハブ化することを避ける。

### 4.4 navigation-historyの責務限定(循環依存の回避)

- `navigation-history`(フロント`features/navigation-history/`、バックエンド`navigation_history/`)は「履歴データの保持と問い合わせ(戻る/進む候補の取得等)」のみを所有する。
- 実際のナビゲーション実行(ディレクトリ移動そのもの)は呼び出し側(`file-list`または`routes/`)が行う。`navigation-history`から`file-list`を呼び出すことはしない。これにより`file-list`⇔`navigation-history`間の循環依存を回避する。
- **SHOULD-25対応(`shared/state/current-directory`との役割分担): `navigation-history`は「現在のカレントディレクトリ」の値そのものを自身のフィールドとして複製保持しない。** これは5.2節が禁じる状態の複製に該当するため明示的に禁止する。役割は以下のように分離する。
  - `shared/state/current-directory.svelte.ts`(5.2節の共有状態所有モジュール)は「現在値」のみを唯一の所有者として保持する。
  - `navigation-history`が保持するのは「過去に訪問したディレクトリの履歴(戻る/進む用のスタック)」という**現在値とは別種のデータ**である。
  - 履歴への追記トリガーは、`navigation-history`が`current-directory`所有モジュールの更新イベント(4.1項1.のイベント通知の仕組み)を購読し、値が変化するたびに履歴へ追記する形に限定する。`navigation-history`が独自に現在値を書き換えたり、`current-directory`をポーリングして複製したりすることは禁止する。
  - 「戻る/進む」操作自体は`navigation-history`が履歴から次の遷移先を算出して呼び出し側へ返すのみであり、実際の移動(`current-directory`の更新)は呼び出し側(`file-list`または`routes/`)が`current-directory`所有モジュールの公開更新関数を呼ぶことで行う(1つ目の箇条書きと整合)。

### 4.5 shared/ipc/の構成(単一集約ファイルの禁止)

- `shared/ipc/`はTauriコマンドと1:1対応する薄いラッパ関数のみを置く。ビジネスロジック・状態保持を持たない。
- feature別にファイルを分割する(例: `shared/ipc/fs.ts`, `shared/ipc/keymap.ts`, `shared/ipc/archive.ts`等)。**単一の`ipc.ts`へ集約することは禁止する**(旧`ui_constants.ts`1001行の再来を避けるため)。

## 5. 状態管理方針(architecture-guardian指摘 MUST-7 対応)

旧リポジトリの`page_init_*`/`page_setters_*`等のGod module化(既存調査3.2/3.3)は、複数画面から参照される共有状態の所有者が定まっていなかったことが一因である。featureディレクトリを縦割りにしただけではこの問題は再発するため、以下を定める。

### 5.1 各featureが所有する状態の境界

- 各featureは自身のUIローカル状態(そのfeature内でのみ参照される状態)を自身のディレクトリ内で完結して所有する。他featureや`routes/`はこれを直接参照しない。参照が必要な場合は4節のコマンドレジストリ/イベント経由で問い合わせる。

>
> 上記の原文は、`routes/+page.svelte`がfeatureの状態を合成目的で読む実装(Phase 1で既に存在する`fileListState.entries`等の直接読み取り、および§3.1.2で確定したPhase 3検索featureの設計)と文言上衝突する。§4.1経路②(routes層での合成)の定義も「複数featureのコンポーネント・ハンドラの配置・受け渡しのみ」であり、feature内部状態値の読み取りそのものは明示的にカバーしていない。

>
> - 各featureは自身のUIローカル状態を自身のディレクトリ内で完結して所有する。**書き込み(状態を変更する更新関数の呼び出し)は所有feature自身に限る。** 他featureがこれを直接importして書き込むことは禁止する。

### 5.2 複数featureが参照する共有状態の唯一の所有者

- 複数featureから参照される共有状態(例: カレントディレクトリ、選択中ファイル集合)は、`shared/`配下に単一の所有モジュールを設ける(例: `shared/state/current-directory.svelte.ts`, `shared/state/selection.svelte.ts`)。
- 各featureはこの共有状態を「読む」ことはできるが、更新は所有モジュールが公開する更新関数(例: `setCurrentDirectory()`)を通じてのみ行う。featureが独自に同種の状態を複製して保持することを禁止する。
- 新規の共有状態を追加する場合は、`docs/architecture/traceability.md`に所有モジュールと読み書きするfeatureの一覧を追記し、architecture-guardianの確認を経ること(所有者不在の状態を増やさないため)。

### 5.3 Svelte 5 runes / storeの採用方針

- featureローカル状態: Svelte 5のrunes(`$state`, `$derived`等)を基本とする。コンポーネント/モジュールスコープでの完結を優先する。
- 5.2の共有状態(所有モジュール): runesベースの状態を`.svelte.ts`ファイルに定義し、モジュールスコープの単一インスタンスとしてexportする(Svelte 5におけるstore代替パターン)。
- Svelte 4の`writable`/`derived`等のstore APIは、runesとの混在による混乱を避けるため新規コードでは採用しない。
- この採用方針は影響範囲が全feature・全共有状態に及ぶため、本書全体のREQUIRES_HUMAN_APPROVALの対象に含める。

## 6. 永続化I/Oの責務所有(architecture-guardian指摘 MUST-8 対応、第2次改訂でMUST-15/17/SHOULD-21を追加反映)

旧提案では永続化I/Oの責務が`config/`(設定)・`keymap/`(キーマップ既定値)・`navigation_history/`(履歴永続化)の3モジュールに分散し、所有者が未定義であった。第1次改訂で「`config/`への一元化」自体は定めたが、schema型の依存方向が`config/ → keymap::schema`という**feature内部への直接依存**になっており、§4.2「`<feature>/`間の直接依存禁止」に抵触し、かつ`keymap/`が読込済みデータを受け取る経路も未定義で循環依存(`keymap/ → config/ → keymap::schema`)を招く恐れがあった(MUST-15)。第2次改訂で以下の通り一意化する。

### 6.1 Rust側: 永続化I/O単独所有とスキーマ型の配置(MUST-15対応)

- **永続化I/Oは`config/`が単独で所有する。**(**SHOULD-29対応**: 「将来`shared/persistence/`へ改称する場合も含め」という記述は撤回する。`config/`を`shared/`配下へ移すと、`<feature>/ → shared/`の一般規定により`<feature>/`から`config/`への直接参照が自動的に許容されてしまい、§4.2の「featureは`config/`を直接参照しない」という制約が無効化されるため、`config/`は今後も2節で定義した`app/`と`<feature>/`の間の独立レイヤーの位置に置き、`shared/`配下へは移さない。)`keymap/`・`navigation_history/`はいずれも自身でファイルの読み書きを行わない。
- **スキーマ型(struct/enum)は`keymap/`・`navigation_history/`ではなく`shared/schema/`(例: `shared/schema/keymap.rs`, `shared/schema/navigation_history.rs`)に定義する。** これにより:
  - `config/`の依存方向は `config/ → shared/schema/` のみとなり、`<feature>/`への直接依存が発生しない(§4.2のレイヤー規定に適合)。
  - `keymap/`・`navigation_history/`の依存方向も `<feature>/ → shared/schema/` のみとなり(既存の`<feature>/ → shared/`規定と同一)、`config/`への依存が発生しない。
  - 結果として`config/`と`<feature>/`は互いを直接参照せず、ともに`shared/schema/`のみに依存する形になるため、循環依存は構造的に生じない。
- `config/`はこれらのschema型のインスタンスを受け取り(6.2節参照)、シリアライズ・ファイルパス決定・実際の読み書きを一元的に実行する。
- キーマップの既定値(デフォルトのキー割当)やキー処理ロジックそのものは`keymap/`が引き続き所有する(schema型の「置き場所」のみを移設するのであり、既定値算出やキー解決ロジックまで`shared/`に移すものではない)。

### 6.2 読込済みデータのfeatureへの受け渡し方向(MUST-15対応、MUST-26で経路を訂正)

- 起動時: `app/`(bootstrap)が`config/`を呼び出して永続化データ(`shared/schema/`型のインスタンス)を読み込み、各`<feature>/`の初期化関数へ引数として注入する。`keymap/`・`navigation_history/`が自ら`config/`をimportして読みに行くことはしない。
- 実行時の保存・再読込は**フロントエンド側から**行う。フロントエンドのfeatureが値の変更を永続化したい場合は`shared/ipc/config.ts`(6.4節)を介して`config/`が公開するTauriコマンド(例: `config_save_keymap`, `config_save_navigation_history`)を呼び出す。これはブラウザ側プロセスからネイティブ側プロセスへの実際のIPC呼び出しであり、Rustコード同士の直接`use`は発生しない。
- **MUST-26対応(訂正): Rustコード内で`<feature>/`のハンドラが`config/`のTauriコマンドを「呼び出す」機構は存在しない**(Tauriコマンドはフロントエンド`invoke()`からのみ起動され、Rustプロセス内でコマンド同士を呼び合う仕組みではない)。したがって、Rust側`<feature>/`が実行時に最新の設定・履歴値を必要とする場合は、6.3節に定める`app/`からの注入経路のみを用いる。`<feature>/`のコマンドハンドラが`config/`を`use`することは、実行時再読込の目的であっても行わない。

### 6.3 Rust側ランタイム状態の所有者(SHOULD-21対応、MUST-26で経路を訂正)

- 読込済み設定・履歴データの実行時保持(Tauriの`State<T>`)は`config/`が単独で所有する。`config/`は`State<ConfigState>`(内部にMutex等で保護された`shared/schema/`型のインスタンス群を保持する構造体)をTauriへ`manage()`登録する。
- `keymap/`・`navigation_history/`は自身のモジュール内に`State<T>`を持たない。実行時の最新値が必要な場合は、`app/`(bootstrap)が起動時に注入した値をfeature側でも保持し続ける(スナップショット。以後の更新はフロントエンド経由の6.2節の保存コマンドが`config/`側の`State<ConfigState>`を更新し、次回起動時または明示的な再注入で反映する)。**Rustコード内で`<feature>/`が`config/`の`State<ConfigState>`や取得用コマンドを直接呼び出すことはしない**(MUST-26により、Rust側featureから`config/`への実行時アクセス経路そのものを設けない)。具体的な再同期方式(スナップショットの更新タイミング等)はSPEC-0300-0003/0007の詳細設計時に決定する(本書ではRust側ランタイム状態の所有者が`config/`であること、および`<feature>/`から`config/`への直接呼び出し経路を設けないことのみを確定する)。

### 6.4 フロントエンド側: 永続化経路の一本化(MUST-17対応)

- **フロント側の各featureが自身の設定・履歴を永続化する際は、`shared/ipc/config.ts`(config向けTauriコマンドの薄いラッパー、4.5節)経由の**みを用いる**(ホワイトリスト方式)。** `shared/ipc/fs*`の書き込み系ラッパー、ブラウザの`localStorage`/`sessionStorage`/IndexedDB、Tauri公式プラグイン(fs/store系)、その他いかなる経路であっても、アプリケーション自身の設定・履歴の永続化に用いることを禁止する(**SHOULD-28対応**: 個別手段を列挙するブラックリストではなく、「`shared/ipc/config.ts`経由のみを許可する」という許可経路の限定によって、将来追加されうる新しい永続化手段も自動的に対象に含める)。`shared/ipc/fs*`はあくまでユーザーが操作対象とするファイル・ディレクトリへのI/O(SPEC-0300-0005等)のためのものである。
- これにより、Rust側で`config/`に一元化した永続化I/O単独所有の原則が、フロント側からの抜け道(featureが`fs`書き込みコマンドを使って独自にJSONを書く「第二の永続化経路」)によって崩れることを防ぐ。

### 6.5 影響範囲

- この変更により、SPEC-0300-0003(キーボード/キーマップ)・SPEC-0300-0007(ジャンプリスト/履歴)の永続化処理は`config/`に一本化される。スキーマ型の配置が`keymap::schema`/`navigation_history::schema`から`shared/schema/`へ変更されたことに伴い、`docs/architecture/traceability.md`の該当行は本改訂に合わせて更新済み。

## 7. モジュール分割の定量基準(ISS-0005への回答案)

**注意: 以下は architecture-mapper による提案であり、確定ではない。architecture-guardianによる検証、および人間承認を経て初めてISS-0005を解消する。ただし本節はISS-0005のうち「モジュール分割の定量基準」のみに対応するものであり、技術スタックの具体バージョン(8節参照)・状態管理方式(本改訂の5節で新たに対応)は別事項として扱う。詳細は`docs/architecture/traceability.md`のISS-0005該当箇所を参照。**

### 7.1 上限(既存の内部DoDを踏襲、除外条項を有界化)

- 通常のロジックファイルは400行を超えないことを上限の目安とする(旧`srp_refactor_plan.md`のDoDを踏襲。既存調査3.3)。
- 400行に近づいた場合、まず「複数の責務が混在していないか」を確認し、責務単位で分割する(行数だけを機械的な分割トリガーにしない)。
- **除外条項の有界化(MUST-4対応):** 純粋なスキーマ/型/定数ファイルであっても、行数上限を無制限に免除しない。上限を600行まで緩和できるのは、以下の条件1・条件2を両方満たす場合に限る。**(SHOULD-24対応: 表記を(i)(ii)から条件番号へ統一)**
  1. 単一のfeature(または`shared/`内の単一の意味的領域)に属し、他ドメインの定数・型を含まないこと
  2. 実質的にデータ定義のみであり、分岐・副作用を伴うロジックを含まないこと
  条件1・条件2のいずれかを満たさない場合は通常ファイルと同じ400行を上限とする。旧`ui_constants.ts`(1001行、複数ドメインの定数を1ファイルに集約)は条件1を満たさないため、新プロダクトでは機能(feature)ごとにファイルを分割する対象となる。
- **行数基準の機械チェック化(MUST-4対応):** `docs/architecture/proposals/SPEC-0500-0001.md` §4で提案するパス整合性チェックスクリプト基盤に相乗りする形で、CIまたはローカルスクリプトによりファイル行数を走査し、上記の上限(400行、条件付き600行)を超えるファイルを検出・警告する仕組みの導入を推奨する。しきい値超過を自動ブロックするか警告に留めるかは、CI要否(ISS-0008)の確定と合わせて決定する。

### 7.2 下限(過度な細分化への歯止め、実測値に基づく調整)

- 旧リポジトリでは1〜20行程度の極小ファイルが約50件存在した(既存調査3.2: `page_actions.ts`1行、`events.ts`2行等)。**SHOULD-11対応として、この実測値(20行未満が約50件)に合わせ、新プロダクトでは以下のいずれにも該当しない20行未満の単独ファイルは、隣接する責務のモジュールへ統合することを基本とする。**
  - (a) barrel/re-exportのみを行うindexファイル
  - (b) 複数モジュールから広く参照される単一の型/定数で、独立した意味的境界を持つもの
  - (c) 生成コード

### 7.3 ディレクトリ粒度

- **SHOULD-43の主張は正しい**: `app/src/lib/features/keyboard/key-dispatch.ts:108-110`の`if (ctx.isSettingsOpen) { return false; }`と、呼び出し元`app/src/routes/+page.svelte:79-81`の`if (handled) ke.preventDefault();`により、「`false`を返す=チェーンを打ち切りつつ`preventDefault`しない」は既存のプレーンな`boolean`で成立している。第4次改訂の`{matched, preventDefault}`拡張の撤回は妥当であり、新設ステップ(`true`=処理済み+`preventDefault`、`false`=打ち切りのみ)も型変更なしで破綻なく表現できる。
- **SHOULD-44の整理も正しい**: `key-dispatch.test.ts:124-140`の`makeContext`は`DispatchContext`の全フィールドを明示構築しているため、2フィールド追加時に更新が必要なのはこのヘルパー1箇所であり、`expect(handled).toBe(...)`の8箇所は変更不要である。
- MUST-40(b)(`inputFocused`を`features/search/search-state.svelte.ts`が所有し、routesはgetter参照+setter配線のみ)は§5.1改訂案・SHOULD-19と整合する。`DispatchContext`はイベントごとに再構築される(`+page.svelte:37`)ため、getter参照で十分でありリアクティビティ上の問題もない。
- SHOULD-45〜47(docstringのR-109-2-1限定、`navigation.ts`冒頭コメントの更新指示、`moveFocusColumn`の`totalCount`/`applySelectToggle`の`visibleCount`・`focusedIndex`の視覚空間化)は、`navigation.ts:1-3,23-43`・`selection.ts:81-85`の実装と照合して正確である。

ただし以下のMUST-41・MUST-42は、**発注者へ付議する3件セット(§5.1改訂案・§4.1改訂案・SPEC-0300-0010追補案)の内容そのものの誤り**であるため、付議前に修正すること。MUST-43・MUST-44はcode-generator着手前でよい。

### MUST(発注者付議前に解消)

- **MUST-41(§3.1.4: 新設優先2の挿入位置がR-14〈設定画面中の全面抑止〉を暗黙に弱める)**
  §3.1.4は新設ステップを「優先1の直後、**`isSettingsOpen`ガードおよび**優先2(exit)より前」に置くとしている。しかしR-14「設定画面の表示中はグローバルリスナーでの処理を行わず、設定画面側のキー処理に委ねる」は現行実装で`dispatchKeydown`の第2段(`key-dispatch.ts:108`)として表現されており、その**前**に処理を行うステップを挿入すると、`isSettingsOpen && isSearchInputFocused`が同時に真の場合に`onSearchAction`が発火し`preventDefault`される=「グローバルリスナーでの処理を行わない」というR-14の保証が破れる。これは第4次改訂でarchitecture-guardianが指摘し、mapper自身が§3.1.4の欠陥リスト2番として引用した「`isSettingsOpen`(R-14)ですら優先1の後に評価されるという保証を暗黙に変更する」という批判と、同じ構造の問題である(批判の対象を自ら再現している)。
  なお、SHOULD-50が要求する「優先2(exit)の抑止」は、**`isSettingsOpen`ガードの直後**に新設ステップを置けば同様に達成できる(現行実装ではexit判定は`isSettingsOpen`ガードより後にある)。
  解消案(いずれか一意に決めること): (a) 新設ステップを`isSettingsOpen`ガードの**直後**(exit判定の直前)に置くと§3.1.4・追補案の表の注記を書き換える(推奨。R-14への影響がゼロになり、SHOULD-50の目的も満たす)。(b) 現位置を維持するなら、R-14の意味変更(設定画面表示中でも検索入力欄の4キーは処理される)を追補案の「付随する変更点」に明記し、両フラグが同時に真になりうるか(§3.1.4のMUST-44も参照)の判断とあわせて発注者の承認対象に含める。

### MUST(code-generator着手前に解消。発注者付議は妨げない)

- **MUST-43(§3.1.4: `inputFocused`のリセット責任が未定義で、恒久的な入力抑止に陥りうる)**
  MUST-40(b)の設計は`inputFocused`の更新を検索`<input>`の`onfocus`/`onblur`のみに依存している。しかし検索バーが閉じる経路(R-106の3経路)では`<input>`要素が**DOMから外れる**ため、主要ブラウザでは`blur`イベントが発火しない(フォーカスは暗黙に`body`へ移る)。この場合`inputFocused`が`true`のまま残り、新設ステップが以後すべてのキーを抑止し続けて`Ctrl+Q`/`Ctrl+,`以外が一切効かなくなる。§3.1.5はcancel直後に`containerEl?.focus()`を呼ぶ設計だが、Svelteのアンマウントと`.focus()`の実行順に依存する不安定な回避であり、設計として依拠すべきでない。
  解消案: `search-state.svelte.ts`側で「`active`が`false`になる操作(`cancel()`/`close()`/空クエリ確定)では必ず`inputFocused`も`false`にする」ことを状態モジュールの不変条件として明記する(または公開getterを`active && inputFocused`として定義する)。所有者を確定した以上、そのライフサイクル(いつ偽に戻るか)も同じ節で確定させること。

- **MUST-44(§3.1.3: `toRealIndex`が`-1`を返す場合の扱いが未定義)**
  §3.1.3は`toVisualIndex`が`-1`を返した場合の防御的フォールバック(視覚インデックス0とみなす)のみを定めているが、`toRealIndex`側の`-1`(範囲外)に対する扱いが未定義である。特に`toggleFocused()`は`visible`が0件のとき`applySelectToggle`が`focusedIndex=0`を返し、`toRealIndex(0, entries, [])`が`-1`となるため、そのまま格納すると`focusedIndex=-1`が状態に入る。あわせて、`focusedEntry()`が`entries[focusedIndex]`(実配列基準)を返す仕様のため、フォーカス中エントリが`visible`に含まれない状態で`toggleFocused`/`selectFocused`が呼ばれると**非表示エントリを選択する**(R-123「対象は`filteredEntries`のみ」に反する)。通常運用ではR-120により到達しない経路である旨は§3.1.3に書かれているが、`toVisualIndex`と同様に防御的な規定(例: `toRealIndex`が`-1`のときは`focusedIndex`を更新しない、`toggleFocused`は`focusedEntry`が`visible`に含まれない場合no-op)を明記し、unit-test-writerのテスト対象に含めること。
