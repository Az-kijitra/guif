## 1. 仕様

- **[R-01] フロントエンドに標準的なテストフレームワークを導入する。** vitest 等の標準フレームワークを採用し、独自のテストランナースクリプトに依存しない。
- **[R-02] Rustバックエンドのテスト基盤を標準的な形で整備・拡充する。**
- **[R-03] カバレッジ確保の対象は「MVP機能全般に均等」とする。** SPEC-0300-0001 が定める基本7機能すべてを、偏りなくテスト対象とする。
- **[R-04] 特定操作を優先する方針は採らない。** 破壊的操作(Copy/Move/Delete 等)を他機能より優先してカバレッジを確保する方針は、人間レビューにより不採用と確定している。
- **[R-05] テスト基盤の整備を後回しにしない。** テスト体制の強化は本プロダクトの目的(SPEC-0100-0001 R-03「将来の機能拡張を容易にするための基盤整備」)の一部であり、機能実装完了後の追加作業として扱わない。

### 1.1 開発・テスト用の設定フォルダの上書き(第2版で新設)

- **[R-06]【第2版・発注者決定 2026-10-01(ISS-0180)/ 設計 MUST-108】debug ビルド(`cfg(debug_assertions)` が真のビルド)では、環境変数 `GUIF_CONFIG_DIR` により、アプリ設定ディレクトリ(`config.toml`、`ui-state.toml`、`navigation.toml`、`viewer-window.toml` ほか、各仕様が「アプリ設定ディレクトリ」に置くファイルすべて)の場所を上書きできる。** release ビルドではこの環境変数を読まない。
  - **[R-06-1]** 環境変数が**存在しない**場合だけ、既定のアプリ設定ディレクトリを使う。
  - **[R-06-2]** 環境変数が存在し、値が (a) 空、(b) 空白のみ、(c) Unicode として解釈できない、(d) 絶対パスでない、のいずれかの場合は**起動エラー**とし、既定のアプリ設定ディレクトリへ落ちない(上書きのつもりで実データを使ってしまうことを防ぐ)。起動エラーの表し方(標準エラーへの出力と終了コード等)は設計工程。
  - **[R-06-3]** 有効な値の場合はそのフォルダを使い、無ければ作る。
  - **[R-06-4]【設計 MUST-109】上書きが有効になった場合は、画面への表示・状態メッセージは設けないが、標準エラー出力へ `[config] override dir: <path>` を1行出す**(`<path>` は使うフォルダの絶対パス)。
  - 各機能仕様の「アプリ設定ディレクトリ」の規定(SPEC-0300-0009 R-77、SPEC-0300-0010 R-45、SPEC-0300-0013 §10、SPEC-0300-0015 R-425)は release ビルドの振る舞いとしてそのまま有効であり、本条項はそれらを改訂しない。利用者向けの機能・設定ではない(SPEC-0100-0004 R-03 の範囲内)。
- **[R-07]【第2版・発注者決定 E3(2026-10-01)/ 2026-10-02】実アプリ(Tauri + WebView2)を Chrome DevTools Protocol(WebView2 のリモートデバッグ)で操作・計測する E2E テストを `app/e2e/` に置く。** 新しい依存は追加せず、Node(22 以上)の標準機能で実装する。見た目の受入基準の検証方法(表示倍率の固定、計測・比較の方法)は SPEC-0300-0017 §16.0 / R-995 を正本とする。
- **[R-08]【第2版・設計 MUST-109】E2E は、利用者の実データ(既定のアプリ設定ディレクトリ)に触れないことを次の手順で保証する。**
  1. 一時フォルダの絶対パスを `GUIF_CONFIG_DIR` に指定して debug ビルドを起動する。
  2. 標準エラー出力の `[config] override dir: <path>` の行を確認し、行が無い、または `<path>` が指定したパスと一致しない場合は、アプリへの入力(キー・マウス・CDP による操作)を**1つも送らずに**テストを中止する(アプリを終了させる)。
  3. テストの終了後、既定のアプリ設定ディレクトリ(およびその中のファイル)の更新日時がテストの開始前から変わっていないことを検査し、変わっていればテストを失敗とする。
