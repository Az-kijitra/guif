## 1. 仕様

- **[R-01] 技術スタックは Tauri + SvelteKit + Rust を維持する。** 他フレームワーク/他言語への置き換えは行わない。
- **[R-02] スタック自体の見直しは本プロダクトの目的としない。** アーキテクチャのクリーン化(SPEC-0100-0001 R-01)は、スタック内部の構造改善として実施する。
- **[R-03] フロントエンド/バックエンドの責務分離を明示的に設計する。** 既存同様、フロントエンド(SvelteKit)とバックエンド(Rust/Tauri)の間の唯一のIPC経路は Tauri の `invoke()` によるコマンド呼び出しおよびイベント通知とする。
- **[R-04] モジュール分割の粒度に基準を設ける。** 既存プロダクトで発生した極端なファイル細分化(1〜20行程度の極小モジュールが多数)と、逆に肥大化した巨大ファイルの併存を、新プロダクトでは避ける。具体的な行数基準・分割方針はアーキテクチャ設計工程で定める(→ ISS-0005)。

## 2. 根拠・出典

- R-01/R-02: 要件ドラフト §2.1「維持する。」(ヒアリングメモ Q3。質問文脈は Tauri + SvelteKit + Rust というスタックを維持するか見直すかを問うもの)
- R-03: 既存調査 2.3(Tauri v2 の invoke() が唯一のIPC経路、80コマンドが bootstrap.rs に登録)に基づく現行構造の踏襲。スタック維持(R-01)の帰結として記載。
- R-04: 既存調査 3.2「app/src/lib直下の200以上のpage_*.tsファイルのうち、1〜20行程度の極小ファイルが多数存在する」「一方でui_constants.ts(1001行)、GitPanel.svelte(938行)のような大きいファイルも残っている」、および 3.3(SRPリファクタの経緯、DoD「400行を超えるファイルを作らない」)。
  - 注記: 既存調査 3.3 は「過度な分割が新たな複雑性になっているかどうかは本調査のスコープでは判断しない」としている。したがって R-04 は「基準を設ける」ことのみを定め、具体的な基準値は確定しない。

## 3. 本仕様では確定しない事項

- Tauri / SvelteKit / Rust の具体バージョン(既存は Tauri 2, Svelte 5。新プロダクトで同一とするかは未確認)
- モジュール分割の定量基準、ディレクトリ構成、状態管理方式(→ ISS-0005。architecture-mapper 以降の工程で設計)
