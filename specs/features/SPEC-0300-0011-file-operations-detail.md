### 0.2.2 本追補に反映したオーケストレーター設計判断(2026-09-23、ISS-0047)

| # | 対応 issue | 確定事項 | 反映先 |
|---|---|---|---|
| 1 | ISS-0047 | **完全削除の起動手段は、既存の `delete` アクションのハンドラ内で Shift 修飾の有無を判定する固定分岐として実現する。** 新規アクションIDは追加しない。キーマップ(`config.toml`)のカスタマイズ対象は `delete` アクションのキー割当のみとし、「Shift 修飾を伴う場合は完全削除」という意味づけはハンドラの固定仕様とする。機構としては、**キーマップ照合が成立した後にハンドラ内で追加の修飾キーを検査して分岐する**方式(SPEC-0300-0010 §3.1 の分類 (b))を採る | R-56-4(確定条項化), R-56-4-1〜R-56-4-3, AC-46-5(差し替え), AC-46-6, AC-46-7, AC-76-1, §12-j。機構側の正本は SPEC-0300-0010 R-18 / R-18-1 / §3.1 #4 |

- 判断の理由(ISS-0047 の根本原因): SPEC-0300-0010 R-34 の救済照合(Shift のみを修飾キーとするイベントは `Shift+` を除いた割当文字列とも照合する)により、`Shift+Delete` は既に `delete` アクションに一致する。したがって完全削除に独立したアクションID(例: `delete_permanent`)を新設すると、同一ハンドラ内で `delete` と当該アクションの双方が `Shift+Delete` に一致し、ISS-0033 と同型の競合(同一ハンドラ内の解決順が未規定)が生じる。ハンドラ内の固定分岐とすればアクション照合は既存のまま成立し、この競合を回避できる。
- **機構の分類に関する訂正(ISS-0049、spec-reviewer 指摘 2026-09-23)**: 本追補の当初記述は本方式を「`Ctrl+Q` / `Ctrl+,` と同じパターン」と説明していたが、これは不正確であった。`Ctrl+Q` / `Ctrl+,` は**キーマップ照合を迂回する先取り判定**(SPEC-0300-0010 §3.1 分類 (a) / R-12 優先1)であり、本方式は**キーマップ照合を通過した後にハンドラ内で修飾キーを検査する分岐**(同 §3.1 分類 (b))である。後者には `main` にも先例があり、Shift 併用のフォーカス移動で範囲選択へ分岐する処理(SPEC-0300-0009 R-60、`main:app/src/lib/page_list_focus.ts:36-43`)が同一の機構である。したがって本方式は「`main` に存在しない新規パターン」ではなく、既存機構に新しい意味づけ(完全削除)を与えるものである。
- **完全削除という意味づけ自体はオーケストレーターの設計判断であり、調査資料(`main`)に対応する実装は存在しない。** 本仕様では該当条項に【導出】を付す。

## 5. 衝突解決(宛先に同名が既に存在する場合)

- **[R-30] コピー / 移動のすべての経路で衝突を検出し、確認を経ずに上書きする経路を設けない。** 経路の種類に応じた扱いは次のとおりとする。【発注者確認 2026-09-23(§0.2 #2)および発注者追加確認 2026-09-23(§0.2.1 #2、ISS-0043 RESOLVED)。`main` は貼り付け経路のみ確認ダイアログを持ち、`fs_copy` / `fs_move` / `fs_copy_pairs` を直接呼ぶ経路は preflight に存在チェックが無いため無条件上書きになるという非対称があった: 調査§1.3 の表, §7-2 / main:app/src-tauri/src/fs_ops_preflight.rs:97-140,142-169】

| 経路 | 例 | 衝突検出時の扱い |
|---|---|---|
| UI を持つ経路 | キーボード / 編集メニュー / コンテキストメニューからの貼り付け | 確認ダイアログ(上書き / スキップ / キャンセル)を表示し、利用者の判断に従う(R-31〜R-34) |
| UI を持たない経路 | 将来の自動化、内部APIの直接呼び出し、テストからの呼び出し等 | エラーコード `conflict` を返して当該項目を**拒否する**。上書き・スキップ・自動リネームのいずれも自動では行わない |

  - **[R-30-1]** R-30 を満たすため、衝突検出は「貼り付けフロー限定のフロントエンド処理」ではなく、コピー/移動のバッチ実行に共通する経路(preflight またはバックエンドの実行ループ)で行う。具体的な配置は architecture-mapper 工程の設計に委ねるが、「UI 層を経由しない呼び出しでも、衝突が黙って上書きされない(`conflict` で拒否される)」ことを満たすこと。【発注者追加確認 2026-09-23(§0.2.1 #2)。`main` は確認をフロントエンドの貼り付けフローのみに持たせていた: 調査§1.3-1〜6 / main:app/src/lib/actions/clipboard.ts:83-114】
    - **[R-30-2]** 上書き / スキップは、UI 経路での利用者の判断(またはそれに相当する明示的な解決指示)が与えられた場合にのみ実行される。解決指示のないバッチ実行で衝突項目を上書きしてはならない。【導出。R-30 の表(UI を持たない経路は `conflict` で拒否)を実装上満たすための必要条件として明記する】
    - `conflict` は R-85 の実行時エラーコード一覧に既に含まれている(新規追加は不要)。
- **[R-31] 確認ダイアログの選択肢は「上書き」「スキップ」「キャンセル」の3択とする。**【根拠: 調査§1.3-2 / main:app/src/lib/components/modals/PasteConfirmModal.svelte:66-68】

## 13. 受入基準

Phase 2(ファイル操作)の完了判定に用いる。すべて「〜できること」形式でテスト可能な粒度とする。

**受入基準の役割分担(ISS-0025 の再発防止)**: 「当該キー(Ctrl+C / Ctrl+X / Ctrl+V / Delete / **Shift+Delete** / F2 / Ctrl+N / **Ctrl+Shift+N**)を押すと当該アクションが発火する」ことの検証は **SPEC-0300-0010 §9.7(AC-41〜AC-44、`new_folder` に対応する AC-49、`delete` の Shift 修飾分岐に対応する AC-50 / AC-51、および `delete` のカスタム割当に対する Shift 禁止に対応する AC-53)を正本**とする。本仕様の受入基準は**発火後の結果**のみを検証し、キー発火の検証を二重に持たない。フォーカス/選択状態そのものの検証は SPEC-0300-0009 を正本とする。

### 13.1 操作対象の決定とクリップボード

- **[AC-01]** 複数のエントリを選択した状態でコピーを実行すると、選択した全件が貼り付け対象になること。(R-10, R-19)
- **[AC-02]** 選択が0件でフォーカスのみがある状態でコピー / 切り取り / 削除を実行すると、フォーカス中の1件が対象になること。(R-10, R-11)
- **[AC-03]** 選択もフォーカスも無い状態でコピー / 切り取りを実行すると、何も起こらずステータス表示のみが出ること(エラーダイアログが出ないこと)。(R-10)
- **[AC-04]** アプリでコピーを実行した後、OS のエクスプローラ等の別アプリに貼り付けると、当該ファイルが貼り付けられること(OS クリップボードに書き込まれていること)。(R-15)
- **[AC-05]** アプリで切り取りを実行した後、別アプリへ貼り付けると移動として扱われること(ドロップ効果が MOVE として設定されていること)。(R-16)
- **[AC-06]** 別アプリでコピーしたファイルを、アプリ内で貼り付けできること。(R-15, R-18)
- **[AC-06-1]** 別アプリ(OS のエクスプローラ等)で**切り取り**したファイルをアプリ内で貼り付けた場合、コピーとして処理され、**元の場所のファイルが残っていること**(移動として扱われないこと)。(R-16, R-19, R-19-1。**ISS-0044-e RESOLVED 2026-09-23**、追補2で新設)
- **[AC-07]** 空白領域を右クリックしたときにも貼り付け項目が表示され、クリップボードが空のときは無効化されていること。(R-14-1)

### 13.2 コピー / 移動

- **[AC-08]** 単一ファイルを別ディレクトリへコピーでき、元のファイルが残っていること。(R-01, R-20)
- **[AC-09]** 単一ファイルを別ディレクトリへ移動でき、元のファイルが無くなっていること。(R-02, R-20)
- **[AC-10]** サブディレクトリを含むディレクトリをコピー / 移動すると、配下の全内容が再帰的に処理されること。(R-20)
- **[AC-11]** 複数選択したファイルとディレクトリを1回の操作でコピー / 移動できること。(R-20)
- **[AC-12]** 別ドライブへ移動した場合(OS のリネームが失敗しフォールバック経路に入る場合)でも、移動が成功していれば成功として報告され、失敗件数に計上されないこと。(R-23)【`main` のバグの修正確認】
- **[AC-13]** 別ドライブへの移動でフォールバックのコピーまたは元削除が失敗した場合は、当該項目が失敗として失敗一覧に現れること。(R-23)
- **[AC-14]** コピー元と貼り付け先が同一ディレクトリになる項目は処理されず、除外件数がステータスに表示されること。(R-25。**ISS-0036 / ISS-0042 は RESOLVED 2026-09-23** により、R-25 は `main` 踏襲のまま確定した。したがって本ACは確定した受入条件である。同一フォルダ内に1操作でコピーを作る手段が無い状態は容認された → R-93)
- **[AC-15]** ディレクトリを自身の配下へ移動 / コピーしようとすると、処理が行われずエラー(`destination_inside_source`)になること。(R-24)
- **[AC-16]** 存在しないディレクトリを宛先に指定した場合、処理が行われずエラー(`destination_not_found`)になること。(R-24)
- **[AC-17]** 対象0件でコピー / 移動を呼び出すと、エラー(`no_items`)になること。(R-24)
- **[AC-18]** コピー / 移動の結果として、成功件数・失敗件数・総件数・失敗一覧が取得できること。(R-22)

### 13.3 衝突解決

- **[AC-19]** 宛先に同名のファイルがある状態で貼り付けを実行すると、確認ダイアログが表示され、「上書き」「スキップ」「キャンセル」の3つの選択肢が提示されること。(R-30, R-31)
- **[AC-20]** 「上書き」を選択すると、宛先の既存ファイルが対象の内容に置き換わること。(R-31)
- **[AC-21]** 「スキップ」を選択すると、衝突した項目は変更されず、衝突していない他の項目の処理は完了していること。(R-31)
- **[AC-22]** 「キャンセル」を選択すると、当該バッチのいずれの項目も処理されないこと。(R-31)
- **[AC-23]** 「リネームして両方残す」に相当する選択肢がダイアログに存在しないこと。(R-31-1)
- **[AC-24]** 衝突が2件以上ある状態で「すべてに適用」をチェックして「上書き」を選択すると、2件目以降の衝突ではダイアログが表示されず、すべて上書きされること。(R-33)
- **[AC-25]** 衝突が2件以上ある状態で「すべてに適用」をチェックして「スキップ」を選択すると、2件目以降の衝突ではダイアログが表示されず、すべてスキップされること。(R-33)
- **[AC-26]** 衝突が2件以上ある状態で「すべてに適用」のチェックを外して「上書き」を選択すると、2件目の衝突で再度ダイアログが表示されること。(R-34)
- **[AC-27]** 「すべてに適用」を外して1件目を「上書き」、2件目を「スキップ」と別々に選択した場合、1件目は上書きされ2件目は変更されていないこと。(R-34)
- **[AC-28]** 確認ダイアログを開いた時点で「すべてに適用」がチェック済みであること。(R-34-1)
- **[AC-29]** UI を経由せずコピー / 移動のバッチ処理を直接呼び出し、宛先に同名項目が存在する場合、当該項目が上書きされずエラーコード `conflict` で拒否されること(自動での上書き・スキップ・リネームが行われないこと)。(R-30, R-30-1, R-30-2)
- **[AC-29-1]** 表示中の一覧に反映されていない同名項目(例: 貼り付け直前に別プロセスが宛先に作成したファイル)に対しても衝突が検出されること。(R-32, R-32-1)
- **[AC-30]** 衝突確認ダイアログを開いた時点で既定フォーカスが「キャンセル」側にあり、Enter のみを押した場合に上書きが実行されないこと。(R-35。**ISS-0037 RESOLVED 2026-09-23** により確定)

- **[AC-46-5]** windows プロファイルにおいて、`delete` の既定キー(`Delete`)を修飾なしで押した場合は対象が OS 標準のごみ箱へ移動し、`Shift+Delete`(同じキー + Shift 修飾)を押した場合は対象が完全削除される(ごみ箱に存在しない)こと。(R-50, R-56, R-56-4, R-56-4-1。**ISS-0047 RESOLVED 2026-09-23** により確定。キー押下で `delete` アクションが発火すること自体の検証は SPEC-0300-0010 AC-42 / AC-50 を正本とし、本ACは分岐後の結果を検証する)
- **[AC-46-6]** vim プロファイル(`input_keymap_profile = "vim"`)においても、`delete` の既定キー(`D`)でごみ箱への移動、`Shift+D`(Shift 修飾あり)で完全削除が実行されること。(R-56-4, R-56-4-1。キー発火の検証は SPEC-0300-0010 AC-50 を正本とする)
- **[AC-46-7]** `config.toml` の `input_keymap_custom` で `delete` のキー割当を **Shift 修飾を含まないキー**(例: `F8`)に変更した場合、変更後のキーでごみ箱への移動、変更後のキー + Shift 修飾(例: `Shift+F8` の押下)で完全削除が実行されること(「Shift 修飾で完全削除」という意味づけを利用者が個別に変更・無効化する設定項目が存在しないこと)。(R-56-4-2、SPEC-0300-0010 R-30 / R-31。**追補2でカスタム割当の前提条件〈Shift 修飾を含まないこと〉を明記: ISS-0048**)
- **[AC-46-8]** UI(コンテキストメニュー等)からの完全削除の起動手段の有無が所定の仕様どおりであること。(R-56-4-3。**ISS-0041 の派生論点(§12-j)確定後に検証する**)
- **[AC-46-9]** `config.toml` の `input_keymap_custom.delete` に Shift 修飾を含むキー(例: `Shift+F8`)を設定した場合、当該割当が採用されず既定値(windows: `Delete` / vim: `D`)が有効なままであり、修飾なしの既定キーでごみ箱への移動、既定キー + Shift 修飾で完全削除が引き続き実行できること。(R-56-4-2-1、SPEC-0300-0010 R-18-2 / AC-53。**ISS-0048 RESOLVED 2026-09-23**、追補2で新設。フォールバック方式の細部・エラー通知の有無は設計工程に委ねられているため本ACの判定対象に含めない)
- **[AC-47]** 削除結果に退避先パスの対応情報が含まれず、Undo に相当する操作が提供されていないこと。(R-52, R-91)

### 13.6 リネーム

- **[AC-48]** フォーカス中のエントリに対してリネームダイアログが開き、新しい名前を入力して Enter で確定するとファイル名が変わること。(R-60, R-61)
- **[AC-48-1]** リネームダイアログを開いた時点で、名前欄に対象の既存ファイル名がプリセットされており、拡張子を除く部分が選択状態になっていること。(R-60-1。**ISS-0044-b: オーケストレーター技術判断 2026-09-23**、追補2で新設)
- **[AC-48-2]** 拡張子を持つファイル(例: `report.txt`)のリネームダイアログを開いた直後に文字列(例: `summary`)を入力して確定すると、拡張子が保持された名前(`summary.txt`)になること。(R-60-1)
- **[AC-49]** リネームダイアログで Escape を押すと、名前が変わらずダイアログが閉じること。(R-61)
- **[AC-50]** 複数選択している状態ではコンテキストメニューのリネームが無効であること。(R-12)
- **[AC-51]** リスト行内でのインライン編集が発生しないこと(リネームは必ずダイアログで行われること)。(R-60)
- **[AC-52]** 空文字または空白のみの名前で確定しようとすると、必須エラーがダイアログ内に表示され、ダイアログが閉じないこと。(R-62 #1, R-63)
- **[AC-53]** `.` または `..` を名前として確定しようとすると `invalid_name` エラーになること。(R-62 #2)
- **[AC-54]** `\` `/` `:` `*` `?` `"` `<` `>` `|` の9文字それぞれについて、当該文字を含む名前で確定しようとすると `invalid_name` エラーになること(9ケースすべて)。(R-62 #3)
- **[AC-55]** 同一ディレクトリに既存の名前へリネームしようとすると `already_exists` エラーがダイアログ内に表示され、ダイアログが閉じずに再入力できること。(R-36, R-63)
- **[AC-56]** リネームの同名衝突時に、上書き確認ダイアログや自動リネームが発生しないこと。(R-36)

### 13.7 新規作成

- **[AC-57]** 新規作成ダイアログで種別「ファイル」と名前を指定して確定すると、現在ディレクトリに0バイトのファイルが作成されること。(R-70, R-73, R-13)
- **[AC-58]** 新規作成ダイアログで種別「フォルダ」と名前を指定して確定すると、現在ディレクトリにディレクトリが作成されること。(R-70, R-73)
- **[AC-59]** 新規作成ダイアログを開いた時点で名前欄が空であり、自動既定名が入っていないこと。(R-71)
- **[AC-60]** 名前を入力せずに確定しようとすると、必須エラーがダイアログ内に表示されること。(R-71)
- **[AC-61]** `new_folder` アクション(既定 `Ctrl+Shift+N`)により新規作成ダイアログが開き、その時点で種別が「フォルダ」になっていること(ダイアログ内で種別を切り替える操作を要さないこと)。(R-72, R-72-1。**ISS-0038 RESOLVED 2026-09-23、案B採用**。キー発火自体の検証は SPEC-0300-0010 AC-49 を正本とする)
- **[AC-61-1]** `new_folder` から開いたダイアログで名前を入力して確定すると、現在ディレクトリにディレクトリが作成されること。(R-72-1, R-73, R-13)
- **[AC-62]** 種別を明示しない入口(既定 Ctrl+N)から開いたダイアログの種別初期値が「ファイル」であること。(R-72-2)
- **[AC-62-1]** コンテキストメニューの「新規作成...」から開いたダイアログの種別初期値が「ファイル」であること(コンテキストメニューが「新規ファイル...」「新規フォルダ...」に分割されていないこと)。(R-72-3)
- **[AC-63]** 既存の名前で新規作成しようとすると `already_exists` エラーがダイアログ内に表示され、ダイアログが閉じずに再入力できること。(R-74)
- **[AC-64]** 新規作成の成功後にダイアログが閉じ、一覧に作成した項目が現れること。(R-76)
- **[AC-65]** 作成直後に名前編集状態(自動リネーム待機)にならないこと。(R-76)
- **[AC-66]** リネームと新規作成で同一の名前検証(AC-52〜AC-54 と同じ結果)が適用されること。(R-62)
- **[AC-67]** 作成した項目のフォーカス/選択が所定の状態になること。(R-77。**ISS-0039 確定後に検証する**)
