## 0. 経緯・出典

### 0.1 発注者の要望(2026-10-16、原文)

> 選択したフォルダ、または、選択したファイルに対して、あらかじめ登録した任意のアプリを起動する機能が必要です。例えば以下のような状況で使います。1. 選択したフォルダ、または、選択したファイルのあるフォルダでWindows Terminalを開く 2. 選択したフォルダ、または、選択したファイルをVS Codeで開く 3. 選択したフォルダ、または、選択したファイルのあるフォルダをExplorerで開く 4. 選択したフォルダ、または、選択したファイルのあるフォルダにおいて、Git管理ツールを開く(Git管理されたフォルダかどうかを問わない)

### 0.2 発注者決定(2026-10-16、変更不可)

- **【確定 #1】すべて登録制とし、既定で4つを登録する。** 要望の4つの例を含め、すべてのアプリを `config.toml` の1つの一覧の要素(名前・実行ファイル・引数・キー)として扱う。利用者が何も登録していなければ、既定の4つ(Windows Terminal / VS Code / エクスプローラー / Git ツール)を使う。組み込みのアプリと利用者が足したアプリは同じ仕組みで動く。設定画面は作らない。
- **【確定 #2】Git ツールの既定は GitHub Desktop とする。** Git で管理されたフォルダーかどうかを問わず起動する。
- **【確定 #3】入口は、アプリごとのキー、メニューバー(「ファイル」メニューの項目)、右クリックメニューの3つとする。** 既定のキーは旧製品と同じ: `Ctrl+Alt+C` ターミナル、`Ctrl+Alt+V` VS Code、`Ctrl+Alt+E` エクスプローラー、`Ctrl+Alt+Shift+G` Git ツール。
  - 右クリックメニュー・メニューバーに外部アプリの項目を置くことは、承認済みの SPEC-0300-0018 R-1110 / AC-1026、SPEC-0300-0020【確定 #2】/ R-1311 が禁じており、SPEC-0100-0005 §4 は外部アプリ起動をスコープ外としている(ISS-0004)。これらの改訂が要る(§13、ISS-0224)。
- **【確定 #4】対象は「フォーカス行・現在のフォルダー・ファイルの選択」とする。** 複数選択していてもフォーカス行だけを対象にする。行が無ければ(空のフォルダー)現在のフォルダーを対象にする。対象がファイルのとき、ターミナル・エクスプローラー・Git ツールにはファイルのあるフォルダーを渡し、エクスプローラーはそのファイルを選んだ状態で開く。VS Code にはファイルそのものを渡す(要望の 2)。~~ZIP の中の項目は対象にしない(無効)。~~(起票時の記録。下の【確定 #6】で置き換え)
- **【確定 #5】(2026-10-16 追加の決定)Git ツールの既定は GitHub Desktop のままとする(「GitHub Desktop のまま」)。** 発注者の PC では GitHub Desktop がアンインストールされた状態とみられる(§0.4.1)が、その場合は既定の登録で「実行ファイルが見つかりません」の表示(R-1571)となることでよい。
- **【確定 #6】(2026-10-16 追加の決定)ZIP は普通のファイルとして扱う(「普通のファイルとして扱う」)。** 本プロダクトには ZIP の中を表示する機能が無いため、「ZIP の中の項目は無効」の規則は設けない。
- **【確定 #7】(2026-10-16 追加の決定)`external_apps` を書くと、書いたものだけになる(「書いたものだけになる」。Q-02)。** マニュアルには既定の4つの登録をそのまま(書き写せる形で)載せる(R-1590)。
- **【確定 #8】(2026-10-16 追加の決定)起票時の【要確認 Q-01〜Q-20】はすべて推奨案とする(「すべて推奨案でよい」)。** → 【確定 Q-01〜Q-20】(§15)。

### 0.3 旧製品の `main` の事実(既存調査。要旨)

- 組み込みの5系統(エクスプローラー / ターミナル / CMD・PowerShell・WSL / VS Code / Git クライアント)は、選択や右クリックした項目にかかわらず、常に現在のフォルダーを渡していた。独自のアプリ(`external_apps`)の `{path}` もファイルのときは現在のフォルダーで、ファイルそのものを渡す手段が無かった。→ 要望(選択したファイル・フォルダーを対象にする)とは異なり、踏襲しない。
- 起動はシェルを通さず、実行ファイルと引数の配列で行い、終了を待たなかった。作業フォルダー・環境変数の指定は無かった。
- 実行ファイルは `explorer.exe` / `wt.exe` / `code` / `github` を PATH から探し、VS Code と GitHub Desktop は決まった場所の候補を順に確かめていた。Windows Terminal が無いと `cmd.exe` に切り替えていた。
- 独自のアプリのキーは組み込みのキーより後に照合され、同じキーは組み込みが勝った。キーの重なり・不正なキーの検証は無かった。
- Git クライアントは GitHub Desktop が前提で、リポジトリかどうかを確かめていなかった。
- 自動テストは無かった。
- 旧製品の設定キー(`external_vscode_path`、`external_git_client_path`、`external_terminal_profile*`、`external_associations`)は持ち込まない(SPEC-0100-0004 R-01。互換性は不要)。

### 0.4 本リポジトリの現状(起票時の確認。規範ではない)

- 外部アプリ起動は無い(SPEC-0300-0009 R-83、SPEC-0300-0010 R-27 で `open_explorer` ほか7つのアクションを削除済み)。
- 外部のプログラムを起動するのは「OSの関連付けで開く」(SPEC-0300-0015 R-405 系、`viewer_os_open_path`)だけである。
- `config.toml` は起動時に1回だけ読み、アプリは書き込まない(SPEC-0300-0010 R-45 / R-53)。
- 【レビュー S-2】メニューバーのアクセスキーの判定は、Ctrl / Meta を伴う `Alt+文字` を除外している(現行 `menubar-activation.test.ts:44-48` で確かめられている。レビューの指摘による)。

### 0.4.1 発注者の PC の事実(2026-10-16、オーケストレーターが読み取りだけで確認。規範ではない)

- `wt.exe` は `%LOCALAPPDATA%\Microsoft\WindowsApps\wt.exe`(アプリ実行エイリアス。再解析ポイント `IO_REPARSE_TAG_APPEXECLINK`)として存在し、そのフォルダーは `PATH` に含まれる。→ 既定のターミナル `program = "wt.exe"`(R-1510)は、R-1540 の 3(エイリアスを「ファイルがある」と扱う)により **この形で解決する見込み**である。実際に起動できることは AC-1550 で確かめる。【レビュー M-2 で「解決する」から改めた】**【承認後の追補 2026-10-17・スパイク S-1】標準ライブラリで「ファイルがある」と判定でき、解決した絶対パスで起動すると対象のフォルダーで開くことを確かめた(§0.9)。**
- VS Code は `%LOCALAPPDATA%\Programs\Microsoft VS Code\Code.exe`(利用者ごとのインストール)にある。`PATH` の `code` は `bin\code.cmd`(バッチファイル)である。→ 既定の VS Code を `Code.exe` の絶対パスとし `code` を使わない理由(R-1541、【確定 Q-06】)と合う。
- `%SystemRoot%\explorer.exe` がある。
- `%LOCALAPPDATA%\GitHubDesktop` には `app-3.5.4\squirrel.exe`、`Update.exe`、`.dead` の印(2026-08-22)だけがあり、`GitHubDesktop.exe` もアンインストールの情報も無い。GitHub Desktop はアンインストールされた状態とみられる。→ この PC では既定の4番目は「実行ファイルが見つかりません」の表示(R-1571)となる(【確定 #5】)。
  - 参考(未確認。ISS-0225 (c)): GitHub Desktop(Squirrel のインストール)は本体を版ごとのフォルダー `app-<版>\` に置き、インストールされている間は最上位に `GitHubDesktop.exe`(本体を起動するための小さな実行ファイル)があるのが普通とされる。既定の `program` の `%LOCALAPPDATA%\GitHubDesktop\GitHubDesktop.exe` はこの最上位のものを指す。インストールされた PC で確かめる。

### 0.5 本仕様を新規に起こした理由(【導出】)

外部アプリ起動は登録・引数・対象・起動・3つの入口・表示を持つ独立した機能であり、右クリックメニュー(SPEC-0300-0018)・メニューバー(SPEC-0300-0020)を新規に起こした前例と同じ規模になる。キー(SPEC-0300-0010)、メニュー(SPEC-0300-0018 / 0020)、文言(SPEC-0300-0019)、テスト(SPEC-0400-0001)は各仕様の新版で本仕様を参照する(§13)。

## 2. 登録(`config.toml`)

- **[R-1500]【確定 #1 / 確定 Q-01】登録は `config.toml` の最上位キー `external_apps`(テーブルの配列。TOML では `[[external_apps]]`)に書く。** 各要素のフィールドは次のとおりとする。

## 4. 引数と置き換え

- **[R-1520]【確定 #4 / 確定 Q-03】引数の中の次の文字列を、対象に応じて置き換える。**

| 書き方 | 置き換える値 |
|---|---|
| `{path}` | 対象そのものの絶対パス(ファイルならファイル、フォルダーならフォルダー) |
| `{dir}` | 対象のフォルダーの絶対パス(対象がフォルダーならそのフォルダー、ファイルならファイルのあるフォルダー) |

- **[R-1521]【確定 #4 / 確定 Q-04】対象がファイルで `args_for_file` が書かれていれば `args_for_file` を、それ以外(対象がフォルダー、または `args_for_file` が無い)は `args` を使う。** `.zip` ファイルも通常のファイルとして扱う(R-1534)。
- **[R-1522]【導出】置き換えは引数の要素ごとに、要素の中の文字列として行う(要素の一部でもよい。例 `/select,{path}`)。** 置き換えは左から1回だけ行い、置き換えた値(パス)の中の `{` `}` `%` などは見直さない。R-1520 の表に無い `{` … `}`(例 `{cwd}`、`{file}`。【導出・レビュー MINOR-6 / D-02】大文字小文字の違う `{PATH}` `{Dir}` も表に無い書き方とする)、対にならない `{` / `}` を含む要素は正しくない(R-1503 の 3)。
- **[R-1523]【導出】置き換えた後の各要素は、そのまま1つの引数として渡す。** 空白・引用符・`;`・`&`・`%`・`,` を含むパスでも分けない・つなげない。アプリが引用符を足したり、文字をエスケープしたりはしない(Windows のコマンドラインへの組み立ては R-1544)。
- **[R-1524]【確定 Q-05】`program` には `{…}` の置き換えを行わない。環境変数の展開(`%NAME%`。R-1540-1)は `program` にだけ行い、`args` / `args_for_file` には行わない(`%` はそのまま渡す)。**
- **[R-1525]【導出】渡すパスの形は、ファイル一覧が持つ絶対パスのままとする。** 区切りは `\`。長いパスの接頭辞(`\\?\`)は付けない。UNC パス(`\\server\share\…`)はそのまま渡す。
  - `{dir}` は、対象がファイルなら、ファイルのパスから最後の `\` とその後を除いた値とする。その結果がドライブの指定だけ(`C:`)になる場合は `C:\` とし、UNC の共有の最上位(`\\server\share`)になる場合は `\\server\share\` とする(どちらも末尾に `\` を付ける。【導出・レビュー MINOR-4 / D-12】)。
  - 対象がフォルダーなら、`{path}` と `{dir}` はファイル一覧が持つフォルダーのパスのまま(末尾の `\` を足しも削りもしない)とする。
  - 【再レビュー MINOR-3】UNC の共有の最上位がフォルダーとして対象になった場合(現在のフォルダーが共有の最上位で行が無い等)は、ファイル一覧が持つ形(`\\server\share` または `\\server\share\`)のまま渡す。どちらの形でも同じフォルダーを指し、起動したアプリの振る舞いは同じになる見込みである(末尾の `\` と空白を含む場合の届き方は R-1587 で確かめる)。

## 10. 安全

- **[R-1580]【確定 #1 / 導出】`config.toml` は利用者が自分で書くファイルとして信頼し、登録されたプログラムをそのまま起動する。** 起動の前に確認のダイアログは出さない(SPEC-0300-0015 R-405-4 と同じ考え方)。
- **[R-1581]【導出 / 導出・レビュー S-7 / D-09】画面(フロントエンド)からバックエンドへは、登録の番号と対象のパス・種別だけを渡す。実行ファイルと引数は、バックエンドが起動時に読んだ登録(既定の4つは R-1510-1 のバックエンドのデータ)から組み立てる。** 画面の側から任意のプログラム・引数を起動できる経路を作らない。`tauri-plugin-shell` は使わず、画面に任意のプログラムを実行する権限(capability)を与えない。バックエンドは画面へ、使える登録の番号・`name`(利用者の登録のときだけ。既定の4つは番号だけ)・使えるキーを渡す。
- **[R-1582]【導出(SPEC-0300-0011 R-89)】起動のバックエンドのコマンドは、SPEC-0300-0011 R-89 の二重の防御の対象とする。** 対象のパスが絶対パスでなければ、ファイルシステムに触れる前に `invalid_path` で拒否する(表示は R-1576)。SPEC-0300-0011 の対象コマンドの表に加える(§13)。
- **[R-1583]【導出】シェル・コマンドプロンプトを通さず(R-1544)、`args` の `%` を展開せず(R-1524)、置き換えた値を見直さない(R-1522)。** フォルダー名・ファイル名に含まれる文字によって、意図しないコマンドが実行されることを防ぐ。`.bat` / `.cmd` を実行ファイルとして認めない(R-1541)。
- **[R-1584]【確定 Q-18 / 導出(SPEC-0400-0001 R-10)】debug ビルドで E2E の範囲(SPEC-0400-0001 R-10)が有効な間は、実行ファイル(R-1540 で解決した後の実体)と対象の両方が範囲のフォルダーの中にある場合だけ起動し、それ以外は起動せずに拒否する(表示は R-1577)。** 判定は R-10-3 / R-10-6 と同じく正規化したパスで行い、判定できなければ拒否する。これにより E2E では既定の4つ(`explorer.exe` 等)は起動しない。SPEC-0400-0001 R-10-5(範囲が有効な間は外部アプリの起動を常に拒否)は、本条項を採るよう SPEC-0400-0001 の新版で改める(§13、ISS-0224 (h))。release ビルドでは本条項は働かない。

## 11. テスト

- **[R-1585]【確定 Q-18 / 導出(SPEC-0400-0001 R-08 / R-10)/ 導出・レビュー S-5 / D-08 / 再レビュー S-A】E2E と、開発時の動作確認を含む CDP での実アプリの操作は、利用者のアプリを起動しない。** すべての E2E と CDP の操作(本機能を対象にしないものを含む)は、次をすべて満たす。
  1. `REFLEXFILES_CONFIG_DIR`(SPEC-0400-0001 R-06 / R-08)と E2E の範囲(同 R-10)を必ず指定し、両方の有効を確かめてから操作する。利用者の設定(既定のアプリ設定ディレクトリ)のまま、登録のキー・メニューの項目を CDP で操作してはならない(既定の4つが利用者のアプリを起動するため)。
